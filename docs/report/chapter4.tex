\subsubsection{ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)}

ในด้านความต้องการที่ไม่ใช่เชิงฟังก์ชัน ระบบได้รับการออกแบบให้ตอบสนองข้อกำหนดสำคัญ 4 ประการ ได้แก่ ประการแรก ด้านประสิทธิภาพ (Performance) กำหนดให้เวลาการตอบสนองคำขอเรียกดูรายการข่าวผ่าน REST API (\texttt{GET /api/news}) เฉลี่ยต่ำกว่า 150 มิลลิวินาทีเมื่อมีข้อมูลจัดเก็บในหน่วยความจำแคช และมีอัตราความหน่วงเวลา (Latency) ในการกระจายข่าวสารใหม่ผ่าน WebSocket ต่ำกว่า 500 มิลลิวินาทีนับจากช่วงเวลาที่ข่าวถูกบันทึกลงระบบสำเร็จ ประการที่สอง ด้านความคงทนและการรองรับข้อผิดพลาด (Reliability \& Fault Tolerance) ความล้มเหลวในการดึงข้อมูลจากแหล่งข่าวใดแหล่งข่าวหนึ่งต้องไม่ส่งผลกระทบต่อรอบการทำงานของแหล่งข่าวอื่น (Isolation of Failures) พร้อมทั้งมีกลไกสำรอง (Fallback Mechanism) รองรับการแสดงผลข้อความสรุปพื้นฐานในกรณีที่บริการ LLM ภายนอกขัดข้อง ประการที่สาม ด้านสถาปัตยกรรมและการขยายตัว (Maintainability \& Extensibility) ออกแบบโครงสร้างซอฟต์แวร์ตามหลักการ SOLID และ GRASP โดยแยกชั้นความรับผิดชอบอย่างชัดเจน ตลอดจนการประยุกต์ใช้ Protocol Interface ตามรูปแบบ Port and Adapter Pattern ในการเข้าถึงคลังข้อมูล และประการสุดท้าย ด้านความเป็นส่วนตัวและการรักษาความปลอดภัย (Privacy \& Usability) ระบบยึดหลักการไม่เก็บข้อมูลระบุตัวตนส่วนบุคคล (Non-PII) และมีแถบขอความยินยอมการใช้งานคุกกี้ตามมาตรฐานการคุ้มครองข้อมูลส่วนบุคคล

\subsubsection{สถาปัตยกรรมการประมวลผลและการจัดกลุ่มเหตุการณ์แบบ 2 ระดับ (Two-Stage Event-Centric Processing Pipeline)}

เพื่อแก้ไขข้อจำกัดดั้งเดิมของระบบจัดกลุ่มข่าวทั่วไปที่มักยุบรวมข่าวในหมวดเดียวกัน (Topic) กลายเป็นเหตุการณ์เดียวกัน ระบบจึงได้รับการพัฒนาสถาปัตยกรรมประมวลผลเหตุการณ์แบบ 2 ระดับ (Two-Stage Event-Centric Processing Pipeline) ดังแสดงในภาพที่ \ref{fig:arch_event_pipeline} ซึ่งครอบคลุมสายการทำงานตั้งแต่การรับเข้าข้อมูลไปจนถึงการนำเสนอบนหน้าเว็บส่วนติดต่อผู้ใช้

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{images/architecture_event_pipeline.png}
\caption{แผนภาพสถาปัตยกรรมการประมวลผลและการจัดกลุ่มเหตุการณ์แบบ 2 ระดับ (Two-Stage Event-Centric Processing Pipeline Architecture)}

สถาปัตยกรรมดังกล่าวประกอบด้วย 5 ขั้นตอนหลัก ดังนี้:
\begin{enumerate}
    \item \textbf{การรับข้อมูลและปรับสภาพข้อความภาษาไทย (Online Ingestion \& Thai NLP)}: เมื่อมีบทความข่าวใหม่เข้าสู่ระบบ โมดูล \texttt{thai\_normalizer.py} จะทำความสะอาดข้อความ ปรับเลขไทยเป็นเลขอารบิก ลบอักขระความกว้างศูนย์ แปลงคำย่อทางการ และจัดระดับสถานที่ตามลำดับชั้น (Location Hierarchy: จังหวัด $\rightarrow$ อำเภอ $\rightarrow$ ตำบล) จากนั้นจึงส่งต่อให้ \texttt{WangchanBERTa} สกัดเวกเตอร์ความหมาย 768 มิติ และ \texttt{thainer-v2} สกัดเอนทิตีชื่อเฉพาะ (บุคคล องค์กร สถานที่)
    \item \textbf{การระบุและจัดกลุ่มจุลเหตุการณ์ (Stage A: Micro-Event Clustering)}: \texttt{StoryService} ทำหน้าที่ตรวจวัดความคล้ายคลึงของเวกเตอร์ (Cosine Similarity) และเอนทิตีกับกลุ่มเหตุการณ์ที่มีอยู่ในหน้าต่างเวลา 72 ชั่วโมง หากมีค่าความคล้ายคลึง $\ge 0.85$ หรืออยู่ในช่วง $[0.74, 0.85)$ ร่วมกับมีเอนทิตีซ้อนทับกัน จะถูกผนวกเข้าสู่กลุ่มจุลเหตุการณ์เดิม (\texttt{StoryRecord}) แต่หากความคล้ายคลึงต่ำกว่า 0.74 ระบบจะสร้างกลุ่มจุลเหตุการณ์ใหม่ขึ้นทันที
    \item \textbf{การเชื่อมโยงเส้นเรื่องมหาภาค (Stage B: Macro Storyline Identification)}: เมื่อเกิดจุลเหตุการณ์ใหม่ \texttt{MacroEventService} จะประเมินเพื่อเชื่อมโยงเข้าสู่เส้นเรื่องมหาภาค (\texttt{MacroEventRecord}) ผ่านคะแนนความสอดคล้องรวม 4 ปัจจัย หากมีคะแนน $\ge 0.72$ และมีเอนทิตีเฉพาะตรงกัน จะเชื่อมโยงเข้าสู่มหากาพย์เดิมพร้อมกำหนดความสัมพันธ์เชิงเวลา (\texttt{precedes} หรือ \texttt{updates}) ภายใต้หน้าต่าง Episode 45 วัน โดยมีกลไกยับยั้งความขัดแย้งระดับจังหวัด (Strict Province-Only Veto) ป้องกันการนำเหตุการณ์ต่างพื้นที่มาผูกรวมกัน
    \item \textbf{การจัดเก็บข้อมูลและความสอดคล้องเชิงความสัมพันธ์ (Persistence \& SST Integrity)}: ระบบใช้สถาปัตยกรรม Single Source of Truth (SST) โดยกำหนดให้ \texttt{StoryRepo} (\texttt{stories\_data.json}) เป็นแหล่งข้อมูลความจริงสูงสุดในการเก็บฟิลด์ \texttt{macro\_event\_id} ในขณะที่ \texttt{MacroRepo} ทำหน้าที่เป็น Dynamic Index พร้อมทั้งมีกระบวนการกู้คืนอัตโนมัติ (\texttt{Reconciliation Engine}) ที่สามารถสร้างดัชนีมหากาพย์ขึ้นใหม่ได้ทันทีหากพบความไม่สอดคล้องของข้อมูล
    \item \textbf{การประมวลผลและนำเสนอแบบแยกอิสระ (Decoupled Presentation \& Synthesis)}: ให้บริการผ่าน REST API (\texttt{/api/macro-events/trending} และ \texttt{/api/stories/trending}) โดยมี \texttt{StoryPresentationService} ทำหน้าที่สังเคราะห์เนื้อหาพร้อมระบบแคช SHA-256 และส่งมอบข้อมูลไปยังหน้าเว็บส่วนติดต่อผู้ใช้แบบ Bento Hub ที่พัฒนาด้วยโครงสร้าง 11 โมดูล ES อิสระ
\end{enumerate}

\subsubsection{สถาปัตยกรรมระบบกลไกป้องกันและควบคุมความถูกต้อง 3 ระดับ (3-Layer Event Verification and Grounded Synthesis Guardrails)}

เพื่อให้ระบบสามารถสังเคราะห์เนื้อหาข่าวหลายสำนักได้อย่างถูกต้อง ปราศจากอาการสร้างข้อมูลเท็จ (Hallucination) และไม่กวาดข่าวผิดชุดเข้ามานำเสนอ ระบบจึงได้วางสถาปัตยกรรมกลไกป้องกันและควบคุมความถูกต้อง 3 ระดับ (3-Layer Guardrails Architecture) ดังแสดงในภาพที่ \ref{fig:arch_pipeline_guardrails}

\begin{figure}[H]
\centering
\includegraphics[width=0.88\textwidth]{images/architecture_pipeline_guardrails.png}
\caption{แผนภาพสถาปัตยกรรมระบบกลไกป้องกันและควบคุมความถูกต้อง 3 ระดับ (3-Layer Event Verification and Grounded Synthesis Guardrails)}
\label{fig:arch_pipeline_guardrails}
\end{figure}

กลไกการควบคุมทั้ง 3 ระดับทำงานร่วมกันอย่างเป็นระบบ ดังนี้:
\begin{enumerate}
    \item \textbf{ชั้นที่ 1: การกำหนดเหตุการณ์และสกัดหลักฐาน (Layer 1: Event Assignment \& Typed Evidence)}: สกัดหลักฐานสำคัญอย่างเป็นระบบ ได้แก่ กริยาการกระทำ (Action), สถานที่ (Location), ผู้เกี่ยวข้อง (Actor) และเวลาเกิดเหตุจริง (\texttt{extract\_event\_time\_evidence}) พร้อมสร้างรหัสเหตุการณ์ถาวรด้วย Content-Anchored Hash ช่วยตัดปัญหาหมายเลขกลุ่มชนกันเมื่อประมวลผลซ้ำ
    \item \textbf{ชั้นที่ 2: การตรวจสอบชุดข่าวผู้สมัครและกรองคำรบกวน (Layer 2: Candidate Validation \& Noise Reduction)}: ยกเลิกการกวาดข่าวด้วยคำพาดหัวแบบสุ่ม (No Blind Keyword Sweeping) ตัดคำระบุเวลา เดือน และปี ที่มักปะปนในพาดหัว (เช่น คำว่า ``ต.ค.'', ``2569'') และประเมินความเกี่ยวข้องระดับบทความผ่าน 3-Stage Relevance Enforcement Gate (Heuristic Filter $\rightarrow$ LLM Classification $\rightarrow$ Safety Guardrail)
    \item \textbf{ชั้นที่ 3: การตรวจสอบความสอดคล้องและโหมดการสังเคราะห์ที่มีหลักฐานอ้างอิง (Layer 3: Headline-Evidence Alignment \& Grounded Synthesis Modes)}: ตรวจสอบความสอดคล้องระหว่างพาดหัวของมหากาพย์กับเนื้อหาข่าวผู้สมัครที่ผ่านเกณฑ์ โดยแบ่งการทำงานออกเป็น 3 โหมดอย่างชัดเจน:
    \begin{itemize}
        \item \textbf{โหมดระงับการสังเคราะห์ (\texttt{status = 'halted\_mismatch'})}: หากไม่มีข่าวใดผ่านเกณฑ์ความสอดคล้องเลย ระบบจะหยุดการสังเคราะห์ด้วย LLM ทันที พร้อมแสดงข้อความแจ้งเตือนว่าชุดข่าวไม่ตรงกับเหตุการณ์ เพื่อป้องกันการกุเนื้อหาเท็จ
        \item \textbf{โหมดรายงานจากแหล่งข่าวเดียว (\texttt{status = 'single\_source'})}: หากมีข่าวผ่านเกณฑ์เพียง 1 สำนัก ระบบจะนำเสนอข้อมูลอย่างโปร่งใสว่าเป็นรายงานจากสำนักข่าวดังกล่าว โดยไม่แสดงข้อความอ้างว่า ``ยืนยันตรงกันทุกสื่อ''
        \item \textbf{โหมดสังเคราะห์หลายแหล่งข่าว (\texttt{status = 'synthesized'})}: หากมีข่าวตั้งแต่ 2 สำนักขึ้นไปยืนยันตรงกัน ระบบจะสังเคราะห์ภาพรวม (Executive Overview) และลำดับเวลา (Chronological Timeline) พร้อมตรวจสอบรหัสอ้างอิงรายประโยค (Citation Audit) เพื่อความถูกต้องสูงสุด
    \end{itemize}
\end{enumerate}

\subsection{กระบวนการดึงข่าวและการเชื่อมต่อ Playwright (Scraping Pipeline)}

ระบบสเกรปข่าวถูกออกแบบให้ทำงานแบบ Asynchronous ทั้งหมด โดยในแต่ละรอบการทำงาน \texttt{ScraperService} จะสร้าง Task สำหรับแต่ละแหล่งข่าวเพื่อดึงข้อมูลพร้อมกัน (Concurrent Scraping) พร้อมทั้งรองรับการดึงหน้าเว็บที่มีการป้องกันด้วย Cloudflare หรือเรนเดอร์เนื้อหาผ่าน JavaScript ผ่าน \texttt{BrowserService} โดยการลงทะเบียนแหล่งข่าวใช้ Decorator \texttt{@register\_source} ดังตัวอย่าง:

\begin{lstlisting}[language=Python, caption={ตัวอย่างการลงทะเบียนแหล่งข่าวด้วย Decorator}]
@register_source("ThaiPBS", "https://www.thaipbs.or.th", "#FF5722")
async def scrape_thaipbs(browser_service: BrowserService) -> list[RawNewsItem]:
    html = await browser_service.fetch_page("https://www.thaipbs.or.th/news")
    return parse_news_cards(html, source="ThaiPBS")
\end{lstlisting}

\subsection{ระบบจำแนกหมวดหมู่และการตัดคำภาษาไทย (Thai NLP Classifier)}

การจำแนกหมวดหมู่ข่าวใช้แนวทางไฮบริด (Hybrid Classification Pipeline) โดยเริ่มต้นจากการสกัดคำสำคัญจากหัวข้อข่าวด้วย PyThaiNLP (\texttt{engine="newmm"}) เพื่อเทียบกับชุดคำศัพท์เฉพาะกลุ่มทั้ง 9 หมวดหมู่หลัก โดยให้ค่าน้ำหนักตามตำแหน่งและความยาวของคำ ในกรณีที่คะแนนจากกฎคำสำคัญไม่ถึงเกณฑ์ความเชื่อมั่นที่กำหนด ระบบจะส่งเวกเตอร์ TF-IDF ของข้อความเข้าสู่โมเดล Support Vector Machine (LinearSVC) ที่ผ่านการเทรนล่วงหน้า และมีโมเดล WangchanBERTa รองรับการประมวลผลข้อความเชิงลึกสำหรับข่าวที่มีบริบทซับซ้อน

\subsection{ระบบเปิดอ่านบทความในตัวเว็บ (In-App Reader) และการสกัดเนื้อหาบทความ}

เพื่อยกระดับประสบการณ์การอ่านข่าวให้มีความต่อเนื่องและปลอดภัย ระบบได้พัฒนาหน้าต่างอ่านบทความฉบับเต็มภายในตัวเว็บ (In-App Modal Reader) สำหรับแสดงผลเนื้อหาข่าวที่ผ่านการสกัดและทำความสะอาดแล้ว โดยทำงานร่วมกับ \texttt{BrowserService} เมื่อผู้อ่านคลิกเปิดอ่านข่าว ระบบจะตรวจสอบว่ามีเนื้อหาที่ผ่านการทำความสะอาดแล้วใน \texttt{AsyncInMemoryCache} หรือไม่ หากมีจะส่งกลับทันทีภายในเวลาต่ำกว่า 10 มิลลิวินาที ในกรณีที่ยังไม่มีข้อมูลในแคช ระบบจะใช้ Trafilatura ร่วมกับ Playwright Chromium ในการดึงและแยกวิเคราะห์เนื้อหาบทความฉบับเต็ม จากนั้นระบบ Backend จะตัดโฆษณา ป้ายแบนเนอร์ แทร็กเกอร์ และองค์ประกอบตกแต่งที่ไม่จำเป็นออกทั้งหมด พร้อมขจัดสคริปต์อันตราย (Anti-XSS) เพื่อความปลอดภัย และแปลงเนื้อหาให้อยู่ในรูปแบบ Markdown สะอาด ก่อนส่งไปแสดงผลบนหน้าต่างอ่านข่าวของเบราว์เซอร์ได้อย่างราบรื่น

\subsection{ระบบสรุปข่าวอัตโนมัติด้วยโมเดลภาษาขนาดใหญ่ (LLM Summarization Pipeline)}

ระบบส่งเนื้อหาข่าวในรูปแบบ Markdown ให้กับ KKU Gen.AI API โดยออกแบบ Prompt ให้ส่งคืนผลลัพธ์เป็นโครงสร้าง JSON ประกอบด้วย บทสรุปกระชับ 2--3 ประโยค ประเด็นสำคัญ 3--5 ข้อ และการวิเคราะห์อารมณ์ของข่าว (Sentiment: Positive, Neutral, Negative) ในภาษาเดียวกับเนื้อหาต้นฉบับ

\subsection{สถาปัตยกรรมระบุประเด็นข่าวและจัดอันดับกระแสข่าวแบบสองชั้น (Two-Layer Story Identification \& Deterministic Trending)}

เพื่อแก้ไขข้อจำกัดของระบบเดิมที่คำนวณการจัดกลุ่มข่าวแบบชั่วคราว (Ad-hoc Clustering) ซึ่งจำกัดกรอบเวลาแข็งตัวไว้เพียง 36--48 ชั่วโมงจนทำให้ข่าวยืดเยื้อแตกกระจาย และมีการพึ่งพา LLM ในเส้นทางการประมวลผลอันดับข่าว ระบบได้ปรับปรุงสถาปัตยกรรมใหม่เป็นแบบสองชั้นที่แยกหน้าที่กันอย่างชัดเจนตามหลักการวิศวกรรมซอฟต์แวร์ ได้แก่ ชั้นที่ 1 การระบุและติดตามประเด็นข่าวแบบออนไลน์คงทน (\texttt{StoryService}) และชั้นที่ 2 เอนจินจัดอันดับกระแสข่าวเชิงสถิติแน่นอน (\texttt{TrendingService})

\subsubsection{การระบุประเด็นข่าวออนไลน์แบบคงทน (Persistent Online Story Identification)}

ในชั้นที่ 1 เมื่อมีบทความข่าวใหม่เข้าสู่ระบบ กระบวนการระบุประเด็นข่าวจะทำงานแบบออนไลน์เชิงเพิ่มพูน (Online Incremental Assignment) ตามแนวคิด Real-Time Story Identification ของ Škvorc และคณะ \cite{skvorc2025realtime} โดยไม่จำเป็นต้องคำนวณจัดกลุ่มข่าวใหม่ทั้งคลังข้อมูล ซึ่งประกอบด้วยขั้นตอนการทำงานสำคัญ 4 ขั้นตอน:

ขั้นตอนแรกคือ การสกัดเวกเตอร์ความหมายหนาแน่น (Dense Semantic Embeddings) โดยนำข้อความพาดหัวข่าวร่วมกับเนื้อหาย่อแปลงเป็นเวกเตอร์ขนาด 768 มิติด้วยโมเดล WangchanBERTa ผ่านการรวมแบบเฉลี่ยถ่วงน้ำหนัก (Masked Mean Pooling) และปรับให้เป็นเวกเตอร์หนึ่งหน่วย ($L_2$ Normalization) ทำให้ผลคูณจุด (Dot Product) มีค่าเท่ากับค่าความคล้ายคลึงโคไซน์ (Cosine Similarity) พร้อมทั้งมีระบบแคชระดับ L1 ป้องกันการเข้ารหัสข้อความซ้ำซ้อน

ขั้นตอนที่สองคือ การสกัดเอนทิตีชื่อเฉพาะ (Named Entity Recognition: NER) โดยใช้โมเดล \texttt{thainer-v2} ของ PyThaiNLP ในการสกัดชื่อบุคคล (PERSON) องค์กร (ORGANIZATION) สถานที่ (LOCATION) และสิ่งอำนวยความสะดวก (FACILITY) ออกจากบทความข่าว

ขั้นตอนที่สามคือ การสืบค้นกลุ่มข่าวผู้ท้าชิงผ่านหน้าต่างเวลา 72 ชั่วโมงแบบไม่ปิดกั้นอายุขัย (Non-capping 72-Hour Candidate Window) โดยระบบจะค้นหากลุ่มประเด็นข่าว (\texttt{StoryRecord}) ที่มีข่าวอัปเดตล่าสุดภายใน 72 ชั่วโมงก่อนเวลาของบทความใหม่ ซึ่งการกำหนดหน้าต่างเวลานี้ช่วยควบคุมขอบเขตความซับซ้อนในการคำนวณโดยไม่จำกัดอายุขัยของประเด็นข่าว ทำให้เหตุการณ์วิกฤตที่ยืดเยื้อ เช่น อุทกภัย สามารถติดตามและผูกโยงข่าวใหม่เข้ากับประเด็นเดิมได้อย่างต่อเนื่องข้ามสัปดาห์

ขั้นตอนที่สี่คือ การตัดสินใจรวมกลุ่มด้วยเกณฑ์สองระดับ (Two-Band Cosine Decision Gate) โดยคำนวณความคล้ายคลึงโคไซน์ระหว่างเวกเตอร์บทความใหม่กับจุดศูนย์กลางของกลุ่มประเด็นข่าว ($\mathbf{c}$):
\begin{equation}
\text{MergeDecision} = \begin{cases} 
\text{Direct Merge} & \text{เมื่อ } \cos(\mathbf{e}_{\text{new}}, \mathbf{c}) \ge 0.85 \\
\text{Confirmed Merge} & \text{เมื่อ } 0.74 \le \cos(\mathbf{e}_{\text{new}}, \mathbf{c}) < 0.85 \text{ และมีเอนทิตีตรงกัน } \ge 1 \\
\text{New Story Cluster} & \text{กรณีอื่น ๆ (สร้างกลุ่มประเด็นข่าวใหม่)}
\end{cases}
\end{equation}
ในกรณีที่มีการรวมบทความเข้าสู่กลุ่มประเด็นเดิม เวกเตอร์จุดศูนย์กลางจะได้รับการปรับปรุงอย่างต่อเนื่องด้วยค่าเฉลี่ยเคลื่อนที่แบบเอกซ์โพเนนเชียล (Exponential Moving Average: EMA) ตามสมการ:
\begin{equation}
\mathbf{c}_{\text{new}} = \alpha \cdot \mathbf{c}_{\text{old}} + (1 - \alpha) \cdot \mathbf{e}_{\text{new}}
\end{equation}
โดยกำหนดค่าน้ำหนัก $\alpha = 0.85$ ช่วยรักษาเสถียรภาพของแกนเรื่องเดิมไม่ให้เบี่ยงเบนเร็วเกินไป พร้อมทั้งปรับตัวรองรับพัฒนาการใหม่ของข่าวได้อย่างยืดหยุ่น นอกจากนี้ กลุ่มประเด็นข่าวจะได้รับการบริหารจัดการวงจรชีวิต (Lifecycle State) ระหว่างสถานะพร้อมทำงาน (\texttt{active}) เมื่อมีข่าวอัปเดตในรอบ 72 ชั่วโมง และสถานะพักตัว (\texttt{dormant}) เมื่อไม่มีความเคลื่อนไหวเกิน 72 ชั่วโมง เพื่อประหยัดทรัพยากรระบบ โดยสามารถฟื้นคืนสถานะสู่ \texttt{active} ได้ทันทีหากมีข่าวด่วนที่เกี่ยวข้องเกิดขึ้นในอนาคต

\subsubsection{เอนจินจัดอันดับกระแสข่าวเชิงสถิติแน่นอน (Deterministic Trending Engine)}

ในชั้นที่ 2 การจัดอันดับกระแสข่าวจะประมวลผลบนกลุ่มประเด็นข่าว (\texttt{StoryRecord}) ที่ผ่านการรวมกลุ่มและบันทึกแล้ว โดยตัดการพึ่งพาโมเดลภาษาขนาดใหญ่ (LLM) ออกจากเส้นทางการคำนวณคะแนนอย่างสิ้นเชิง (Zero LLM in scoring path) ทำให้การจัดอันดับมีความรวดเร็วระดับเสี้ยววินาทีและได้ผลลัพธ์ที่แน่นอนเชิงคณิตศาสตร์ (Deterministic) โดยคำนวณผ่าน 6 มิติเชิงสถิติร่วมกับตัวคูณลดทอนข่าวประจำวัน:
\begin{equation}
\text{FinalScore} = \left( \sum_{i=1}^6 w_i \cdot s_i \right) \times \text{RoutinePenalty}
\end{equation}
โดยมีรายละเอียดของแต่ละมิติคะแนน ดังนี้:
ปริมาณข่าวในรอบ 24 ชั่วโมง ($s_1$ น้ำหนัก $w_1 = 0.25$) คำนวณจาก $s_1 = \ln(1 + N_{\text{recent}})$ เพื่อสะท้อนปริมาณความสนใจของสื่อมวลชน
อัตราเร่งการมาถึงของข่าว ($s_2$ น้ำหนัก $w_2 = 0.30$) คำนวณจากอัตราส่วนระหว่างความถี่ของข่าวในรอบ 24 ชั่วโมงล่าสุดเทียบกับช่วงเวลาฐาน 48 ชั่วโมงก่อนหน้า เพื่อตรวจจับสัญญาณข่าวด่วนที่กำลังปะทุขึ้นในสังคม
ความหลากหลายของสำนักข่าว ($s_3$ น้ำหนัก $w_3 = 0.25$) คำนวณจากฟังก์ชันรากที่สองของจำนวนสำนักข่าวที่ไม่ซ้ำกัน $s_3 = \sqrt{N_{\text{outlets}}}$ พร้อมกลไกลดทอนกรณีสำนักพิมพ์ในเครือเดียวกัน (Syndication Discount) เพื่อให้ข่าวที่รายงานโดยสำนักข่าวอิสระหลายแห่งมีน้ำหนักสูงกว่าข่าวที่คัดลอกกันมา
การลดทอนตามเวลา ($s_4$ น้ำหนัก $w_4 = 0.10$) คำนวณจากฟังก์ชันเอกซ์โพเนนเชียลค่าครึ่งชีวิต 12 ชั่วโมง $s_4 = 2^{-\Delta t / 12}$ เพื่อเปิดทางให้ข่าวสดใหม่ขึ้นมาทดแทนข่าวเก่า
ความแปลกใหม่ของประเด็น ($s_5$ น้ำหนัก $w_5 = 0.05$) คำนวณจากระยะห่างเชิงความหมายของจุดศูนย์กลางประเด็นเทียบกับประเด็นข่าวอื่น $s_5 = 1.0 - \max_{j \ne k} \cos(\mathbf{c}_k, \mathbf{c}_j)$
และคะแนนปฏิสัมพันธ์จากผู้อ่าน ($s_6$ น้ำหนัก $w_6 = 0.05$) คำนวณจากสถิติพฤติกรรมการอ่านข่าวแบบนิรนาม $s_6 = \ln(1 + N_{\text{clicks}} + 2 N_{\text{summaries}} + 3 N_{\text{bookmarks}})$

สำหรับตัวคูณลดทอนข่าวประจำวัน (Routine News Penalty) ระบบได้กำหนดกลไกตรวจจับข่าวที่เกิดขึ้นเป็นวงรอบประจำวัน เช่น ข่าวราคาน้ำมัน ราคาทองคำ พยากรณ์อากาศ และผลสลากกินแบ่งรัฐบาล โดยกำหนดตัวคูณปรับลดคะแนน $\text{RoutinePenalty} = 0.25$ (ลดทอนคะแนนลงร้อยละ 75) ในขณะที่ข่าวทั่วไปมีค่าเท่ากับ $1.0$ กลไกนี้ช่วยป้องกันไม่ให้ข่าวประจำวันแย่งพื้นที่ข่าวกระแสสังคมที่แท้จริง พร้อมทั้งระบบส่งคืนข้อมูลแจกแจงคะแนนครบทุกมิติ (\texttt{TrendingScoreBreakdown}) ทำให้กระบวนการจัดอันดับมีความโปร่งใสและตรวจสอบที่มาได้ทุกขั้นตอน

\subsection{ส่วนนำเสนอและการสังเคราะห์เนื้อหาประเด็นรวม (Story Presentation \& LLM Synthesis)}

สำหรับกลุ่มประเด็นข่าวที่ติดอันดับกระแสความนิยมสูงสุด ระบบจะส่งต่อข้อมูลให้ \texttt{StoryPresentationService} เพื่อสร้างเนื้อหานำเสนอเชิงลึก โดยอาศัยโมเดลภาษาขนาดใหญ่ (KKU Gen.AI) ในการสังเคราะห์พาดหัวข่าวประเด็นรวม (Macro Headline) ที่เป็นกลางและครอบคลุมทุกมุมมอง การสร้างบทสรุปย่อสังเคราะห์ข้ามสำนักข่าว (Multi-Article Synthesis) และการเรียบเรียงไทม์ไลน์พัฒนาการของเหตุการณ์ตามลำดับเวลา (Chronological Timeline Events) พร้อมลิงก์อ้างอิงกลับไปยังสำนักข่าวต้นทาง โดยผลลัพธ์ทั้งหมดจะถูกบันทึกแคชลงในฐานข้อมูลประเด็นข่าวโดยตรง เพื่อลดค่าใช้จ่ายในการเรียกใช้ API ซ้ำซ้อน และหากบริการ LLM ภายนอกขัดข้องหรือไม่ตอบสนอง ระบบมีกลไกสำรองการทำงานแบบอัตโนมัติ (Heuristic Fallback) โดยสลับไปใช้พาดหัวข่าวตัวแทนหลักและเรียบเรียงไทม์ไลน์ตามเวลาเผยแพร่จริง ทำให้ระบบสามารถตอบกลับคำขอด้วยสถานะ HTTP 200 ได้อย่างมีเสถียรภาพเสมอ

\subsection{การจัดกลุ่มมหากาพย์ประเด็นข่าวและส่วนติดต่อผู้ใช้แบบ Bento Hub}

เพื่อยกระดับการติดตามข่าวสารที่มีมิติความซับซ้อนสูง ระบบได้พัฒนา \texttt{MacroEventService} สำหรับเชื่อมโยงกลุ่มประเด็นข่าวย่อย (Sub-events) ที่มีความสัมพันธ์เชิงบริบทเข้าสู่มหากาพย์ประเด็นข่าวขนาดใหญ่ (Macro Storyline) พร้อมทั้งรองรับข้อยกเว้นกรณีวิกฤต (Crisis Exemption) ที่ช่วยให้ข้อมูลภัยพิบัติหรือเหตุฉุกเฉินระดับชาติได้รับการยกเว้นการลดทอนเวลา

ในด้านส่วนต่อประสานผู้ใช้ หน้าแรกของระบบได้รับการออกแบบใหม่เป็น Macro Storyline Bento Hub ซึ่งจัดวางองค์ประกอบแบบ 3 มุมมองหลัก (3-Perspective Matrix) ได้แก่ แถบข่าวเด่นประจำวัน บัตรสรุปประเด็นข่าวพร้อมป้ายสำนักข่าวที่รายงานร่วมกัน (Publisher Filter Pills) และแถบแฮชแท็กเชิงโต้ตอบ (\#Hashtags Ribbon) เพื่อให้ผู้ใช้งานสามารถคลิกสำรวจมุมมองที่หลากหลายของแต่ละสำนักข่าวได้อย่างสะดวก นอกจากนี้ ระบบยังได้จัดเตรียมหน้าต่างติดตามและศูนย์ควบคุมสถานะระบบ (\texttt{frontend/monitoring.html}) สำหรับผู้ดูแลระบบ เพื่อตรวจสอบอัตราการรับเข้าของข่าว สุขภาพของแต่ละสำนักข่าว สถิติการทำงานของแคช และความเสถียรของไปป์ไลน์แบบเรียลไทม์

\subsection{การติดต่อสื่อสารแบบเรียลไทม์ผ่าน WebSocket}

เมื่อมีข่าวใหม่ที่ผ่านการสรุปและจำแนกเรียบร้อยแล้ว \texttt{SocketManager} จะทำการกระจาย Event (\texttt{news:new}) ไปยังเบราว์เซอร์ของผู้ใช้ทุกคนที่กำลังเปิดหน้าเว็บอยู่ เพื่อให้ผู้ใช้ได้รับข่าวสารล่าสุดทันทีโดยไม่ต้องทำการรีเฟรชหน้าต่างเบราว์เซอร์

\subsection{รายละเอียดการทำงานของจุดเชื่อมต่อบริการทั้งหมด (API Specifications)}

ระบบจำแนกและวิเคราะห์ข่าวสารอัตโนมัติได้รับการพัฒนาจุดเชื่อมต่อบริการแบบ REST API ตามมาตรฐาน OpenAPI 3.0 โดยแบ่งแยกความรับผิดชอบออกเป็น 6 กลุ่ม Router หลัก และระบบการตรวจสอบสถานะ (System Probes) รวมทั้งสิ้น 20 จุดเชื่อมต่อบริการ ดังนี้:

กลุ่มที่ 1 จุดเชื่อมต่อบริการกลุ่มประเด็นข่าว (\texttt{StoryRouter} เส้นทางหลัก \texttt{/api/stories}) มีหน้าที่จัดการวงจรชีวิตและการเรียกดูประเด็นข่าวสารที่ผ่านการจัดกลุ่มแบบสองชั้น ประกอบด้วย:
\texttt{GET /api/stories} ใช้สำหรับเรียกดูรายการประเด็นข่าวสาร รองรับพารามิเตอร์การกรองตามหมวดหมู่ (\texttt{category}) สถานะวงจรชีวิต (\texttt{status} ได้แก่ \texttt{active} หรือ \texttt{dormant}) ตลอดจนการแบ่งหน้า (\texttt{limit} ค่าเริ่มต้น 20 และ \texttt{offset}) โดยส่งคืนรายการ \texttt{StoryRecord} พร้อมรายชื่อสำนักข่าวร่วม
\texttt{GET /api/stories/trending} ใช้สำหรับเรียกดูประเด็นข่าวที่กำลังเป็นกระแสความนิยมสูงสุด โดยนำเสนอข้อมูลที่ผ่านการประมวลผลคะแนนจากเอนจินจัดอันดับแบบดีเทอร์มินิสติก (Layer 2) พร้อมรายละเอียดการแจกแจงคะแนน (\texttt{TrendingScoreBreakdown})
\texttt{GET /api/stories/\{story\_id\}} ใช้สำหรับเรียกดูข้อมูลเชิงลึกของประเด็นข่าวรายเรื่อง ประกอบด้วยพาดหัวภาพรวม บทสรุปสังเคราะห์ รายชื่อสำนักข่าวทั้งหมด ไทม์ไลน์พัฒนาการของเหตุการณ์ และรายชื่อบทความข่าวเดี่ยวในกลุ่ม
\texttt{POST /api/stories/\{story\_id\}/summarize} ใช้สำหรับร้องขอการสังเคราะห์เนื้อหาภาพรวมประเด็นข่าว ไทม์ไลน์ และพาดหัวข่าวร่วมผ่านโมเดลภาษาขนาดใหญ่ (KKU Gen.AI) แบบ On-Demand โดยมีกลไกตรวจสอบแคชเพื่อป้องกันการประมวลผลซ้ำ และมีระบบสำรองแบบฮิวริสติก (Heuristic Fallback) รองรับกรณีที่โมเดลภาษาภายนอกไม่ตอบสนอง

กลุ่มที่ 2 จุดเชื่อมต่อบริการกลุ่มมหากาพย์ประเด็นข่าว (\texttt{MacroEventRouter} เส้นทางหลัก \texttt{/api/macro-events}) ทำหน้าที่บริหารจัดการประเด็นข่าวขนาดใหญ่ที่มีความเชื่อมโยงกันข้ามหมวดหมู่และยืดเยื้อ ประกอบด้วย:
\texttt{GET /api/macro-events} ใช้สำหรับดึงรายการมหากาพย์ประเด็นข่าวทั้งหมด โดยสามารถกรองตามสถานะและข้อยกเว้นกรณีวิกฤต (\texttt{crisis})
\texttt{GET /api/macro-events/trending} ใช้สำหรับดึงมหากาพย์ข่าวที่กำลังได้รับความสนใจสูงสุดเพื่อนำไปแสดงผลบนพื้นที่เด่นของหน้าหลัก Bento Hub
\texttt{GET /api/macro-events/\{macro\_id\}} ใช้สำหรับดึงรายละเอียดโครงสร้างมหากาพย์ข่าว ความเชื่อมโยงระหว่างประเด็นย่อย (Sub-events) และไทม์ไลน์ภาพรวมเหตุการณ์

กลุ่มที่ 3 จุดเชื่อมต่อบริการข้อมูลข่าวสารหลัก (\texttt{NewsRouter} เส้นทางหลัก \texttt{/api}) ทำหน้าที่ให้บริการข้อมูลบทความข่าวเดี่ยวและการสกัดเนื้อหา ประกอบด้วย:
\texttt{GET /api/news} ใช้สำหรับดึงรายการบทความข่าวสาร รองรับพารามิเตอร์การแบ่งหน้า (\texttt{page}, \texttt{page\_size}) ตัวกรองหมวดหมู่ (\texttt{category}) ตัวกรองสำนักข่าว (\texttt{source}) และการค้นหาด้วยคำสำคัญ (\texttt{search}) โดยมีระบบแคชระดับ L1 และรองรับ HTTP 304 Not Modified ผ่านส่วนหัว ETag
\texttt{GET /api/news/content} ใช้สำหรับสกัดเนื้อหาบทความข่าวฉบับเต็มในรูปแบบ Cleaned Markdown ผ่าน Trafilatura และ Playwright สำหรับนำไปแสดงผลบนหน้าต่าง In-App Modal Reader
\texttt{GET /api/categories} ใช้สำหรับเรียกดูรายชื่อ 9 หมวดหมู่ข่าวภาษาไทยที่ระบบรองรับ พร้อมรหัสสีและข้อมูลสถิติ
\texttt{GET /api/sources} ใช้สำหรับเรียกดูรายชื่อสำนักข่าวทั้งหมดที่ลงทะเบียนและเปิดใช้งานในระบบ (\texttt{@register\_source})
\texttt{GET /api/status} ใช้สำหรับตรวจสอบสถานะรอบเวลาการทำงานของสเกรปเปอร์และจำนวนข่าวสะสมในระบบ
\texttt{GET /api/image} ใช้เป็นบริการ Reverse Proxy สำหรับดึงและแคชรูปภาพหน้าปกบทความข่าว เพื่อแก้ไขปัญหาการจำกัดการเข้าถึงข้ามโดเมน (CORS) และการป้องกัน Hotlinking ของเว็บไซต์ต้นทาง

กลุ่มที่ 4 จุดเชื่อมต่อบริการนำเข้าบทความเฉพาะกิจ (\texttt{CollectRouter} เส้นทางหลัก \texttt{/api}) ประกอบด้วย:
\texttt{POST /api/collect-md} รับข้อมูล URL ของบทความข่าวเดี่ยวจากผู้ใช้ เพื่อสั่งให้ระบบทำการดึงเนื้อหา สกัดบทความ ตัดคำ และจำแนก 9 หมวดหมู่โดยทันทีแบบ On-Demand

กลุ่มที่ 5 จุดเชื่อมต่อบริการจัดอันดับกระแสและการมีส่วนร่วม (\texttt{TrendingRouter} เส้นทางหลัก \texttt{/api/news}) ประกอบด้วย:
\texttt{GET /api/news/trending} ใช้สำหรับเรียกดูข่าวเดี่ยวที่ติดกระแสความนิยม (คงไว้เพื่อความเข้ากันได้ย้อนหลังกับระบบเวอร์ชันเดิม)
\texttt{POST /api/news/engage} และ \texttt{POST /api/news/engagement} รับข้อมูลเหตุการณ์การมีส่วนร่วมของผู้อ่านแบบนิรนาม (\texttt{click}, \texttt{summary\_view}, \texttt{bookmark}, \texttt{share}) เพื่อนำไปคำนวณเป็นคะแนนปฏิสัมพันธ์ของข่าวโดยไม่มีการเก็บข้อมูลส่วนบุคคล

กลุ่มที่ 6 จุดเชื่อมต่อบริการศูนย์ควบคุมและติดตามสถานะระบบ (\texttt{MonitoringRouter} เส้นทางหลัก \texttt{/api/monitoring}) ประกอบด้วย:
\texttt{POST /api/monitoring/auth} ใช้สำหรับตรวจสอบรหัสผ่านลับของผู้ดูแลระบบ (\texttt{admin\_secret}) และสร้างโทเค็นเซสชันความปลอดภัย
\texttt{GET /api/monitoring/verify} ใช้สำหรับตรวจสอบความถูกต้องของโทเค็นเซสชันผู้ดูแลระบบ
\texttt{GET /api/monitoring/stats} ใช้สำหรับดึงข้อมูลสถิติสุขภาพของระบบ การใช้หน่วยความจำ RAM อัตรา Throughput การทำงานของสเกรปเปอร์ และอัตราความสำเร็จของแคช (Cache Hit Ratio)
\texttt{POST /api/monitoring/scrape-now} ใช้สำหรับส่งคำสั่งให้ระบบเริ่มรอบการสเกรปข่าวทุกสำนักทันทีแบบ Asynchronous
\texttt{POST /api/monitoring/clear-cache} ใช้สำหรับสั่งล้างข้อมูลในแคชหน่วยความจำ แคช HTTP ETag และแคชบทสรุปประเด็นข่าว
\texttt{POST /api/monitoring/test-source} ใช้สำหรับทดสอบการเชื่อมต่อและการแยกวิเคราะห์เนื้อหาของสำนักข่าวรายแห่งที่ระบุ

นอกจากจุดเชื่อมต่อบริการ REST API ข้างต้นแล้ว ระบบยังมีจุดเชื่อมต่อบริการสำหรับตรวจสอบสถานะระดับโครงสร้างพื้นฐาน (System Probes) ได้แก่ \texttt{GET /livez} (Liveness Probe ยืนยันการทำงานของโปรเซส), \texttt{GET /readyz} (Readiness Probe ตรวจสอบความพร้อมของระบบจัดเก็บข้อมูลและ Chromium Headless), \texttt{GET /sw.js} (บริการ Service Worker รองรับการแคชออฟไลน์แบบ Progressive Web App) และช่องทางการสื่อสาร WebSocket ผ่าน Socket.IO สำหรับผลักดันเหตุการณ์ข่าวใหม่ (\texttt{news:new}) แบบสองทิศทาง

\subsection{รายละเอียดส่วนต่อประสานและปุ่มควบคุมทั้งหมดของระบบ (Complete UI Controls \& Buttons Catalog)}

เพื่ออำนวยความสะดวกในการใช้งานของผู้ใช้ทุกกลุ่ม ระบบได้รับการออกแบบส่วนติดต่อผู้ใช้เป็น 2 ส่วนหลัก ได้แก่ ส่วนต่อประสานผู้อ่านข่าวทั่วไป (Bento Hub SPA บนไฟล์ \texttt{frontend/index.html}) และศูนย์ควบคุมและติดตามสถานะระบบสำหรับผู้ดูแล (Ops Console บนไฟล์ \texttt{frontend/monitoring.html}) โดยองค์ประกอบของปุ่มควบคุม ตัวเลือกปฏิสัมพันธ์ และหน้าต่างโมดอลทั้งหมดจำแนกได้ดังนี้:

ในส่วนต่อประสานผู้อ่านข่าว Bento Hub (\texttt{frontend/index.html}):
ปุ่มแบนเนอร์แจ้งเตือนข่าวใหม่ลอยตัว (Floating Unread Articles Banner Button) เรียกใช้ฟังก์ชัน \texttt{\_\_loadUnreadArticles()} จะปรากฏขึ้นบริเวณกึ่งกลางด้านบนของหน้าจอเมื่อมีข่าวใหม่เข้ามาผ่าน WebSocket พร้อมแสดงข้อความจำนวนข่าวที่เพิ่งมาถึง เมื่อผู้ใช้คลิกปุ่ม ระบบจะเลื่อนหน้าจอกลับขึ้นสู่ด้านบนสุด (Smooth Scroll) และนำข่าวใหม่เข้าสู่ตารางแสดงผลทันทีโดยไม่ต้องรีโหลดหน้าเว็บ
ปุ่มปิดแบนเนอร์ข่าวใหม่ (Banner Dismiss Button) เรียกใช้ฟังก์ชัน \texttt{\_\_dismissNewArticlesBanner()} อยู่บริเวณมุมขวาของแบนเนอร์ข่าวใหม่ เพื่อให้ผู้ใช้สามารถปิดการแจ้งเตือนได้หากยังไม่ต้องการโหลดข่าวใหม่ในทันที
ปุ่มตราสัญลักษณ์และชื่อระบบ (Brand Navigation Control) บริเวณมุมบนซ้ายของแถบนำทาง เมื่อผู้ใช้คลิกจะคืนค่ากลับสู่หน้าหลัก Bento Hub โดยทำการล้างตัวกรองหมวดหมู่และคำค้นหาทั้งหมด
ปุ่มเปิดประวัติการอ่านข่าว (Reading History Button) เรียกใช้ฟังก์ชัน \texttt{\_\_showHistory()} เพื่อเปิดหน้าต่างโมดอลแสดงรายการบทความที่ผู้ใช้เคยเปิดอ่าน ซึ่งบันทึกอยู่บน LocalStorage ของเบราว์เซอร์
ปุ่มเปิดรายการข่าวที่บันทึกไว้ (Bookmarks Button) เรียกใช้ฟังก์ชัน \texttt{\_\_showBookmarks()} เพื่อเปิดหน้าต่างโมดอลแสดงรายการข่าวที่ผู้ใช้ได้กดบันทึกคั่นหน้าไว้สำหรับการอ่านภายหลัง
ปุ่มเปิดการตั้งค่าและความเป็นส่วนตัว (Settings \& Privacy Button) เรียกใช้ฟังก์ชัน \texttt{\_\_openSettings()} สำหรับเปิดหน้าต่างโมดอลตั้งค่าสิทธิ์คุกกี้ การปรับธีมการแสดงผล และการจัดการข้อมูลส่วนบุคคลตามมาตรฐาน PDPA
แถบปุ่มแท็บหมวดหมู่ข่าว (Category Navigation Tabs) ประกอบด้วยปุ่มสลับหมวดหมู่ข่าวภาษาไทยทั้ง 9 หมวดหมู่หลัก พร้อมปุ่ม "ทั้งหมด (All)" เพื่อดูข่าวรวม และปุ่ม "สำหรับคุณ (For You)" ซึ่งแสดงข่าวที่สอดคล้องกับความสนใจจากพฤติกรรมการอ่าน
แถบปุ่มคัดกรองสำนักข่าว (Publisher Filter Pills) เป็นชุดปุ่มรูปแคปซูลแสดงรายชื่อและสีประจำสำนักข่าว (เช่น ThaiPBS, ไทยรัฐ, เดลินิวส์, มติชน ฯลฯ) ที่อนุญาตให้ผู้ใช้คลิกเลือกเพื่อดูข่าวเฉพาะสำนักพิมพ์ที่สนใจได้
แถบปุ่มแฮชแท็กประเด็นข่าว (\#Hashtags Ribbon) เป็นปุ่มตัวเลือกแฮชแท็กของประเด็นข่าวเด่น ช่วยให้ผู้ใช้สามารถคลิกสำรวจข่าวสารในเหตุการณ์เดียวกันได้อย่างรวดเร็ว
แถบค้นหาและปุ่มล้างคำค้น (Search Input \& Clear Button) กล่องป้อนข้อความค้นหาข่าวแบบ Real-time พร้อมปุ่มกากบาท [$\times$] สำหรับล้างคำค้นหาเพื่อคืนค่ารายการข่าวทั้งหมด
ปุ่มบนการ์ดข่าวสารและประเด็นข่าว (Card Action Controls) ซึ่งติดตั้งอยู่บนบัตรข่าวทุกใบ ประกอบด้วย ปุ่มเปิดบทสรุปผู้บริหาร AI (Executive AI Briefing Button รูปดาวสี่แฉก) สำหรับเปิดโมดอลสรุปเนื้อหาสังเคราะห์และ Sentiment, ปุ่มเปิดอ่านบทความฉบับเต็มในตัวเว็บ (In-App Reader Modal Button) สำหรับอ่านเนื้อหา Cleaned Markdown แบบเต็มหน้าต่าง, ปุ่มบันทึกคั่นหน้า (Bookmark Toggle Button) สำหรับเพิ่มหรือยกเลิกการบันทึกข่าว, ปุ่มแชร์ข่าว (Share Button) สำหรับเรียกใช้ Web Share API ของระบบปฏิบัติการหรือคัดลอกลิงก์ไปยังคลิปบอร์ด และปุ่มเปิดหน้าเว็บข่าวต้นฉบับ (External Source Link Button) สำหรับเปิดลิงก์ข่าวจริงในแท็บใหม่
ปุ่มควบคุมการแบ่งหน้า (Pagination Controls) ประกอบด้วยปุ่มหน้าก่อนหน้า (Previous Page Button), ปุ่มระบุหมายเลขหน้า (Page Number Buttons) และปุ่มหน้าถัดไป (Next Page Button) สำหรับเลือกดูข่าวสารในหน้าต่าง ๆ
ปุ่มควบคุมในหน้าต่างโมดอล (Modal Action Buttons) ประกอบด้วยปุ่มปิดหน้าต่างโมดอล [$\times$], ปุ่มล้างประวัติการอ่านทั้งหมด (Clear All History Button) และปุ่มลบรายการเดี่ยวออกจากประวัติหรือบุ๊กมาร์ก
ปุ่มควบคุมความเป็นส่วนตัว PDPA (Privacy \& Consent Controls) ประกอบด้วยปุ่มยินยอมการใช้งานคุกกี้ (Accept Cookies Button), ปุ่มปฏิเสธคุกกี้ (Reject Button) และปุ่มล้างข้อมูลสถิติความสนใจ (Clear Preference Data Button) เพื่อให้ผู้ใช้สามารถลบประวัติความสนใจทั้งหมดออกจากเบราว์เซอร์ได้ทันที

ในส่วนศูนย์ควบคุมและติดตามสถานะระบบสำหรับผู้ดูแล (\texttt{frontend/monitoring.html}):
ปุ่มสลับการแสดงผลรหัสผ่าน (Password Visibility Toggle Button) บนฟอร์มยืนยันตัวตน เพื่อสลับการแสดงผลรหัสผ่านระหว่างจุดวงกลมกับข้อความธรรมดา
ปุ่มเข้าสู่ระบบคอนโซล (Admin Login Submit Button) สำหรับส่งรหัสผ่านลับของผู้ดูแลระบบไปยังเซิร์ฟเวอร์เพื่อตรวจสอบสิทธิ์และรับโทเค็น
กล่องสลับการรีเฟรชข้อมูลอัตโนมัติ (Auto-refresh Toggle Checkbox) สำหรับเปิดหรือปิดการส่งคำขอดึงสถิติสุขภาพของระบบทุก 5 วินาที
ปุ่มรีเฟรชสถานะด้วยตนเอง (Manual Refresh Button) สำหรับสั่งให้เบราว์เซอร์ส่งคำขอดึงสถิติล่าสุดทันทีโดยไม่ต้องรอรอบเวลา
ปุ่มสั่งเริ่มรอบการสเกรปข่าวทันที (Scrape Now Button) สำหรับสั่งการให้ระบบเริ่มกระบวนการสเกรปข่าวด่วนจากทุกสำนักพร้อมกัน
ปุ่มสั่งล้างแคชระบบ (Clear Cache Button) สำหรับสั่งให้เซิร์ฟเวอร์ล้างข้อมูลใน L1 Memory Cache, แคช HTTP ETag และแคชบทสรุปประเด็นข่าว
ปุ่มทดสอบแหล่งข่าวรายสำนัก (Test Source Probe Buttons) ซึ่งมีอยู่ประจำแต่ละสำนักข่าว เพื่อให้ผู้ดูแลสามารถกดทดสอบการเชื่อมต่อและการสกัดข้อมูลเฉพาะสำนักข่าวนั้น ๆ พร้อมแสดงผลรหัสสถานะและจำนวนบทความที่พบ
ปุ่มออกจากระบบคอนโซล (Logout Button) สำหรับทำลายโทเค็นเซสชันและนำผู้ดูแลกลับสู่หน้าจอยืนยันตัวตนอย่างปลอดภัย

\subsection{ตัวอย่างส่วนต่อประสานผู้ใช้และการแสดงผลจริงของระบบ (System User Interface Demonstration)}

เพื่อแสดงให้เห็นถึงการทำงานจริงของระบบตามสถาปัตยกรรมและข้อกำหนดที่ได้ออกแบบไว้ ในหัวข้อนี้จะนำเสนอตัวอย่างส่วนต่อประสานผู้ใช้ (User Interface) ของระบบจำแนกและวิเคราะห์ข่าวสารอัตโนมัติที่ผ่านการติดตั้งและประมวลผลข่าวจริงในสภาพแวดล้อมปฏิบัติการ โดยครอบคลุม 3 มุมมองหลัก ดังนี้

ประการแรก หน้าต่างหลัก Macro Storyline Bento Hub และแถบกระแสข่าวด่วน ดังแสดงในภาพที่ \ref{fig:ui_home_feed} เป็นหน้าจอแรกที่ผู้อ่านเข้าสู่ระบบ โดยประกอบด้วยองค์ประกอบสำคัญหลายส่วน ได้แก่ แถบวิ่งข่าวด่วนสด (Live Ticker) ด้านบนสุด ซึ่งแสดงสถานะจำนวนข่าวสะสมในคลังข้อมูล (12,178 บทความ) จำนวนข่าวใหม่ในรอบการดึงล่าสุด (15 บทความ) และเวลาอัปเดตล่าสุด ถัดลงมาเป็นแถบนำทางหมวดหมู่ข่าว 9 หมวดหมู่หลักในรูปแบบเม็ดแคปซูล พร้อมแสดงจำนวนบทความข่าวจริงในแต่ละหมวดหมู่ เช่น หมวดสังคม 3,829 ข่าว หมวดการเมือง 3,284 ข่าว หมวดเศรษฐกิจ 1,704 ข่าว หมวดกีฬา 1,252 ข่าว และหมวดบันเทิง 815 ข่าว พร้อมปุ่ม ``สำหรับคุณ'' และ ``ทั้งหมด''

ส่วนสำคัญบริเวณกึ่งกลางหน้าจอคือ บัตรข่าวกระแสหลักขนาดใหญ่ (Featured Hero Bento Card) ซึ่งนำเสนอประเด็นข่าวเด่นอันดับหนึ่งที่ผ่านการคำนวณคะแนนจากเอนจินจัดอันดับแบบดีเทอร์มินิสติก (FEATURED \#01, IMPACT SCORE 9.8) โดยแสดงพาดหัวข่าวสังเคราะห์ภาพรวม บทสรุปย่อ และป้ายสีประจำ 6 สำนักข่าวพันธมิตรที่รายงานตรงกัน ได้แก่ Nation Online, Daily News, Thai Post, Khaosod, The Standard และ Matichon พร้อมป้ายแฮชแท็กของเหตุการณ์ (\#อนุทิน, \#ซักฟอก, \#อภิปราย) และปุ่มสั่งการหลัก ได้แก่ ปุ่มบันทึกคั่นหน้า ปุ่ม ``อ่านบทคัดย่อ'' ปุ่ม ``เจาะลึกประเด็น (10 สื่อ)'' และปุ่ม ``สรุป AI'' นอกจากนี้ ด้านล่างยังประกอบด้วยแถบกรองสำนักข่าวอิสระ (SOURCES) พร้อมจำนวนข่าว ช่องค้นหาข่าวแบบเรียลไทม์ และตารางการ์ดข่าวสารเดี่ยว (Editorial News Grid) ที่แสดงหัวข้อข่าว รูปภาพหน้าปก สำนักข่าว และเวลาที่ดึงเข้าสู่ระบบ

ประการที่สอง หน้าต่างเจาะลึกมหากาพย์ประเด็นข่าวในแถบพัฒนาการเหตุการณ์ตามลำดับเวลา (Progression Timeline Dossier) ดังแสดงในภาพที่ \ref{fig:ui_bento_timeline} จะปรากฏขึ้นเมื่อผู้ใช้คลิกปุ่มเจาะลึกประเด็นข่าวจากหน้าหลัก โดยระบบจะจัดกลุ่มบทความข่าวที่เกี่ยวข้องกับเหตุการณ์เดียวกันเข้ามาไว้ในแฟ้มประเด็นเฉพาะ (Special Dossier) ด้านบนแสดงกล่องบทสรุปภาพรวมพื้นฐาน (Baseline Overview) ซึ่งสกัดจากสำนักข่าวต้นทาง (PPTV Online) ตอบสนองทันทีในเวลา 0 มิลลิวินาที พร้อมปุ่มสั่งการ ``สังเคราะห์ความคืบหน้าด้วย AI''

เมื่อคลิกสังเคราะห์ ระบบจะแสดงแฟ้มผลวิเคราะห์ AI (Event Progression Intelligence Dossier) ในธีม Dark Editorial แสดงป้ายกำกับ AI SOURCED INTELLIGENCE และการวิเคราะห์โทนอารมณ์ของข่าว TONE: NEUTRAL พร้อมบทสรุปสังเคราะห์สำหรับผู้บริหาร (Executive Synthesis Briefing) นำเสนอภาพรวมการประชุม ครม. และการเตรียมพร้อมรับมือการอภิปรายไม่ไว้วางใจ โดยในแถบ ``พัฒนาการเหตุการณ์'' (Timeline) ระบบจะแสดง 5 ลำดับเหตุการณ์หลัก ได้แก่ จุดเริ่มต้น (ครม.เน้นย้ำเร่งเยียวยาอุทกภัย), พัฒนาการหลัก (การเตรียมชี้แจง ม.151, พรรคเพื่อไทยประกาศความพร้อม, และการอนุมัติ ครม.สัญจรอุดรธานี), และความคืบหน้าล่าสุด (การประชุม ครม.สัญจรเน้นแก้ปัญหาเกษตรและยาเสพติด) ซึ่งแต่ละเหตุการณ์กำกับด้วยชิปรหัสอ้างอิงหลักฐานข่าว ได้แก่ \texttt{art\_01}, \texttt{art\_02}, \texttt{art\_03}, \texttt{art\_04} และ \texttt{art\_05} เพื่อให้ผู้อ่านตรวจสอบย้อนกลับได้อย่างโปร่งใส

นอกจากนี้ บริเวณกึ่งกลางหน้าจอยังแสดงแถบตัวกรองมุมมองเฉพาะสำนักข่าว (Filter by Publisher Perspective) ที่ครอบคลุมรายงานข่าวทั้งหมด 46 รายงานข่าว ได้แก่ Matichon (6), The Standard (6), Khaosod (5), Thai Post (5), Bangkokbiznews (5), Nation Online (6), Thairath (4), Daily News (5) และ PPTV HD 36 (2) ด้านล่างแสดงการ์ดข่าวสารเดี่ยวตามลำดับไทม์ไลน์เวลาจริง (Chronology \#01, \#02, \#03) พร้อมประทับตราป้ายรหัสหลักฐาน \texttt{ART\_01}, \texttt{ART\_02}, \texttt{ART\_03} ที่เชื่อมโยงกับชิปอ้างอิงด้านบน เพื่อให้ผู้อ่านสามารถคลิกเพื่อเลื่อนหน้าจอไปยังการ์ดข่าวต้นทางและตรวจสอบความถูกต้องได้อย่างสะดวกรวดเร็ว

\subsection{ระบบเจาะประเด็นข่าวและค้นหาเชิงวิเคราะห์ (Issue Explorer \& In-depth Search)}

นอกจากการสำรวจกระแสข่าวสารสดประจำวันและมหากาพย์เหตุการณ์บนหน้าจอหลักแล้ว ระบบยังได้พัฒนาส่วนต่อประสานสำหรับเจาะประเด็นข่าวเชิงลึก (Issue Explorer Workstation) ผ่านหน้าเว็บ \texttt{/issues} เพื่อรองรับการค้นคว้าและสืบค้นเชิงวิเคราะห์ของนักข่าว นักวิเคราะห์นโยบาย และผู้อ่านทั่วไปที่ต้องการติดตามพัฒนาการของประเด็นข่าวเฉพาะด้านอย่างครอบคลุม

ระบบเจาะประเด็นข่าวทำงานร่วมกับสถาปัตยกรรมอ่านอย่างเดียว (Read-Only Architecture) โดยผู้ใช้สามารถสืบค้นด้วยคำสำคัญทั่วไป หรือใช้ไวยากรณ์การค้นหาขั้นสูง เช่น การใช้เครื่องหมายไปป์ (\texttt{|}) เพื่อหาคำพ้องความหมาย การใช้เครื่องหมายลบ (\texttt{-term}) เพื่อคัดกรองข่าวกีฬาหรือบันเทิงที่ไม่เกี่ยวข้องออก และการใช้เครื่องหมายคำพูดคู่ (\texttt{"..."}) สำหรับวลีเฉพาะเจาะจง พร้อมทั้งมีระบบขยายคำย่อหน่วยงานรัฐและคำพ้องความหมายภาษาไทยโดยอัตโนมัติ

ผลลัพธ์การสืบค้นจะถูกสังเคราะห์และนำเสนอในรูปแบบสถานีทำงาน (Investigation Workstation) ประกอบด้วย 4 องค์ประกอบสำคัญ ได้แก่ แถบสรุปภาพรวมและสถิติประเด็นข่าว (Issue Executive Summary), ตารางแจกแจงมุมมองและสัดส่วนการนำเสนอของแต่ละสำนักข่าว (Publisher Perspective Breakdown) เพื่อแสดงให้เห็นว่าสื่อสำนักใดให้ความสนใจในมิติใดเป็นพิเศษ, ไทม์ไลน์ความเคลื่อนไหวของประเด็นตามลำดับเวลาจริง (Chronological Evolution Timeline) และรายการการ์ดข่าวสารที่จัดกลุ่มตามประเด็นย่อย (Issue Sub-clusters) โดยมีระบบคัดกรองข่าวหลุดประเด็น (Outlier Filtering) ช่วยแยกบทความที่ไม่เกี่ยวข้องออกไปอย่างแม่นยำ พร้อมทั้งมีระบบควบคุมอัตราคำขอแบบ Sliding Window IP Rate Limiting ช่วยรักษาความมั่นคงของเซิร์ฟเวอร์


\subsection{การรักษาเสถียรภาพระดับโพรดักชันและการตรวจสอบก่อนส่งมอบ (Production Reliability \& Pre-flight Smoke Testing)}

เพื่อให้การนำระบบขึ้นสู่สภาพแวดล้อมโพรดักชันบนคลาวด์ร่วมกับ Nginx, Cloudflare CDN และ PWA มีความราบรื่นและปราศจากช่วงเวลาหยุดชะงัก (Zero Downtime) ระบบได้วางกลไกการรับประกันคุณภาพและความน่าเชื่อถือทางวิศวกรรม 3 ส่วนหลัก

ส่วนแรก การขจัดปัญหาความไม่เข้ากันของแคชบนเครือข่ายส่งมอบเนื้อหา (Edge \& Client Cache Invalidation) ระบบได้กำหนดนโยบาย \texttt{NoCacheStaticFiles} บน FastAPI ส่งส่วนหัว \texttt{Cache-Control} ที่ระบุ \texttt{no-cache, must-revalidate} สำหรับไฟล์สคริปต์โมดูล JavaScript ทั้งหมด และเพิ่มตัวแปรระบุเวอร์ชัน (\texttt{?v=3.3.3}) กำกับท้ายการนำเข้าโมดูลย่อย (Sub-module Imports) ทุกไฟล์ พร้อมปรับปรุงการทำงานของ Service Worker ให้ล้างแคชเก่าทิ้งทันทีเมื่อตรวจพบเวอร์ชันใหม่ ช่วยป้องกันไม่ให้เบราว์เซอร์ของผู้ใช้ค้างที่ไฟล์สคริปต์เก่าอันเป็นสาเหตุของข้อผิดพลาดหน้าเว็บขาว

ส่วนที่สอง การจัดการความเข้ากันได้ข้ามสภาพแวดล้อม (Cross-Platform Model Loading Isolation) โดยระบบได้ปรับเปลี่ยนวิธีการโหลดโมเดลตัดคำและเวกเตอร์ภาษาไทยให้อ่านโครงสร้างจากไฟล์ \texttt{tokenizer.json} ผ่านคลาส \texttt{PreTrainedTokenizerFast} โดยตรง ช่วยให้โมเดลสามารถทำงานได้อย่างเสถียรทั้งบนสภาพแวดล้อมการพัฒนา (Windows) และสภาพแวดล้อมคอนเทนเนอร์บนโพรดักชัน (Linux Docker) โดยปราศจากปัญหาความเข้ากันไม่ได้ของ SentencePiece

ส่วนที่สาม สคริปต์ทดสอบความพร้อมก่อนขึ้นโพรดักชันอัตโนมัติ (Automated Pre-flight Smoke Test Script ผ่าน \texttt{scripts/preflight\_test.py}) ซึ่งทำหน้าที่ตรวจสอบเสถียรภาพของระบบก่อนการปล่อยให้ผู้ใช้ภายนอกเข้าใช้งาน ครอบคลุมการทดสอบจุดเชื่อมต่อความพร้อมของระบบจัดเก็บข้อมูล (\texttt{/readyz}), การประมวลผลเอนจินจัดอันดับเทรนด์, การจำลองผู้ใช้จริงผ่าน Headless Chromium เพื่อยืนยันว่าไม่มีข้อผิดพลาดหลุดรอดบน Console, การตรวจสอบสถานะการเชื่อมต่อ WebSocket และความพร้อมของระบบเจาะประเด็นข่าว โดยผลการทดสอบทั้งหมดผ่านเกณฑ์ความสมบูรณ์ร้อยละ 100


\section{การออกแบบและมาตรการความมั่นคงปลอดภัยของระบบ (System Security Design)}
% -----------------------------------------------------------

ความมั่นคงปลอดภัยของระบบ (System Security) และการคุ้มครองความเป็นส่วนตัวของผู้ใช้งาน (Data Privacy) เป็นปัจจัยสำคัญในการพัฒนาเว็บแอปพลิเคชันยุคใหม่ โดยระบบได้ออกแบบมาตรการรักษาความปลอดภัยครอบคลุม 4 มิติหลัก ดังนี้

\subsection{ความมั่นคงปลอดภัยระดับเครือข่ายและเว็บเซิร์ฟเวอร์ (Network \& Gateway Security)}

ในระดับเครือข่าย ระบบได้ติดตั้ง Nginx Reverse Proxy ทำหน้าที่เป็น Gateway จัดการเข้ารหัสช่องทางการสื่อสาร (TLS/SSL Encryption) ทั้งในรูปแบบ HTTPS และ Secure WebSocket (WSS) เพื่อป้องกันการดักฟังข้อมูลระหว่างทาง (Man-in-the-Middle Attack) พร้อมทั้งกำหนดนโยบายจำกัดอัตราการเรียกใช้งาน (API Rate Limiting) เพื่อจำกัดจำนวนคำขอต่อหมายเลข IP ช่วยป้องกันการโจมตีแบบปฏิเสธการให้บริการ (DoS) นอกจากนี้ยังได้กำหนดนโยบายการเข้าถึงข้ามโดเมน (CORS Whitelist) เฉพาะโดเมนของระบบที่ได้รับอนุญาต และติดตั้งส่วนหัวความปลอดภัยมาตรฐาน (HTTP Security Headers) ได้แก่ \texttt{X-Content-Type-Options: nosniff}, \texttt{X-Frame-Options: SAMEORIGIN} และ \texttt{Content-Security-Policy (CSP)} เพื่อป้องกันการโจมตีแบบ Clickjacking และ MIME Confusion

\subsection{การป้องกันการฉีดโค้ดอันตรายและการตรวจสอบข้อมูล (Data Sanitization \& Injection Defense)}

ในด้านการป้องกันการโจมตีเชิงความปลอดภัยและการจัดการข้อมูลอันตราย ระบบมีมาตรการป้องกันที่ครอบคลุมหลายระดับ โดยสำหรับการป้องกัน Cross-Site Scripting (XSS) ข้อมูลเนื้อหาข่าวที่สกัดได้จากเว็บต้นทางอาจมีแท็ก HTML หรือสคริปต์อันตรายแฝงมา ระบบจึงใช้กระบวนการแปลงและกรองข้อมูล (Sanitization) เพื่อกำจัดแท็ก \texttt{<script>}, \texttt{<iframe>}, รวมถึงแอตทริบิวต์ \texttt{onload}, \texttt{onerror} ออกทั้งหมด และแปลงเนื้อหาให้อยู่ในรูป Plain Markdown ก่อนส่งไปแสดงผลบนหน้าจอ In-app Modal นอกจากนี้ เพื่อป้องกันข้อผิดพลาดจาก Malformed Input และ Parameter Tampering ระบบได้บังคับใช้การตรวจสอบโครงสร้างข้อมูลเข้มงวดด้วย Pydantic (Strict Schema Validation) ในทุกจุดรับเข้าและส่งออกของ REST API

สำหรับการป้องกัน Server-Side Request Forgery (SSRF) ส่วนงาน Scraper และ Playwright Service จะรับคำขอและดึงข้อมูลเฉพาะจากรายการสำนักข่าวที่ลงทะเบียนไว้ล่วงหน้า (Source Whitelist) เท่านั้น โดยไม่อนุญาตให้ผู้ใช้ภายนอกส่ง URL เครือข่ายภายในเข้ามาประมวลผลโดยตรง และในส่วนการประมวลผลร่วมกับโมเดลภาษาขนาดใหญ่ (LLM Safety) ระบบได้ออกแบบ System Prompt และโครงสร้าง Delimiter กั้นระหว่างคำสั่งหลักกับเนื้อหาข่าวอย่างรัดกุม เพื่อป้องกันปัญหา Indirect Prompt Injection ไม่ให้ข้อความข่าวลบล้างคำสั่งเดิม (Prompt Jailbreak) ของระบบสรุปข่าวได้

\subsection{การคุ้มครองข้อมูลส่วนบุคคลและความปลอดภัยของคุกกี้ (Privacy \& Cookie Security)}

การคุ้มครองความเป็นส่วนตัวของผู้ใช้งานถูกออกแบบตามหลัก Privacy by Design \& Zero PII กล่าวคือ ระบบไม่มีการจัดเก็บข้อมูลส่วนบุคคลที่สามารถระบุตัวตนได้ (Personally Identifiable Information) เช่น ชื่อ ที่อยู่อีเมล หรือหมายเลขประจำเครื่อง โดยข้อมูลพฤติกรรมความสนใจของผู้ใช้จะถูกประมวลผลเป็นเพียงคะแนนรวมแบบนิรนาม (Anonymous Aggregate Engagement) บนฐานข้อมูลเท่านั้น ในระดับเบราว์เซอร์ คุกกี้ที่ใช้ในระบบมีการกำหนดคุณสมบัติความปลอดภัยเข้มงวด ได้แก่ \texttt{SameSite=Lax} และ \texttt{Path=/} เพื่อป้องกันการโจมตีแบบ Cross-Site Request Forgery (CSRF) พร้อมกำหนดอายุการหมดอายุ (Max-Age) ที่เหมาะสม ตลอดจนติดตั้งแถบแจ้งเตือนขอความยินยอมการใช้งานคุกกี้ (Cookie Consent Banner) ตามมาตรฐาน PDPA และมีฟังก์ชันให้ผู้ใช้สามารถกดล้างสถิติพฤติกรรม (Clear Preference Data) บนเบราว์เซอร์ได้ด้วยตนเองตลอดเวลา


\subsection{การจัดการความลับและการตั้งค่าระบบ (Secrets \& Configuration Management)}

API Key สำหรับเชื่อมต่อกับบริการภายนอก เช่น \texttt{LLM\_API} ของ KKU Gen.AI และการตั้งค่าระบบต่าง ๆ ถูกจัดเก็บไว้ในไฟล์ \texttt{.env} และ Environment Variables ที่แยกต่างหาก โดยมีไฟล์ \texttt{.gitignore} ป้องกันการนำความลับของระบบขึ้นสู่ระบบควบคุมเวอร์ชัน (Git Repository) อย่างเข้มงวด

\section{การทดสอบระบบ}

การรับประกันคุณภาพและความน่าเชื่อถือของระบบ (Quality Assurance \& Reliability) เป็นหัวใจสำคัญในการพัฒนาระบบรวบรวมและวิเคราะห์ข่าวสารอัตโนมัติ ซึ่งต้องทำงานต่อเนื่องตลอดเวลา (24/7 Continuous Operation) และประมวลผลข้อมูลจากภายนอกที่มีความผันผวนสูง โครงงานนี้จึงประยุกต์ใช้ระเบียบวิธีพัฒนาที่ขับเคลื่อนด้วยการทดสอบ (Test-Driven Development: TDD) และสร้างชุดทดสอบอัตโนมัติที่ครอบคลุมการทำงานทุกระดับตั้งแต่การทดสอบระดับหน่วย (Unit Testing) การทดสอบการทำงานร่วมกัน (Integration Testing) การทดสอบกรณีสุดขั้วและสภาวะวิกฤต (Adversarial \& Stress Testing) การทดสอบการประมวลผลพร้อมกัน (Concurrency Testing) และการทดสอบความมั่นคงปลอดภัยตามมาตรฐาน PDPA รวมทั้งสิ้น 423 กรณีทดสอบ (423 Test Cases) ครอบคลุม 39 โมดูลทดสอบบนเฟรมเวิร์ค \texttt{pytest} โดยมีผลการทดสอบผ่านสมบูรณ์ครบทั้ง 423 กรณีทดสอบ (คิดเป็นร้อยละ 100)

\subsection{การทดสอบคุณสมบัติคงที่ทางวิศวกรรมและกรณีสุดขั้ว (In-Depth Technical Testing Methodologies)}

เพื่อให้มั่นใจว่าระบบมีเสถียรภาพภายใต้สภาวะการทำงานจริงที่มีความซับซ้อน ชุดทดสอบได้ออกแบบกรณีทดสอบครอบคลุมคุณสมบัติคงที่ทางวิศวกรรม (Engineering Invariants) และสภาวะสุดขั้วใน 9 ด้านหลัก

ประการแรก การทดสอบความแม่นยำในการระบุประเด็นข่าวมหากาพย์และคุณสมบัติคงที่ P0--P2 (Stage B Macro Invariants \& Province Veto) ได้รับการตรวจสอบอย่างเข้มงวดผ่าน \texttt{test\_macro\_p0\_p2\_invariants.py} ซึ่งครอบคลุมการทดสอบกฎยับยั้งการรวมกลุ่มเมื่อตรงกันเฉพาะชื่อจังหวัด (Province-Only Veto), การรักษาป้ายกำกับ Typed NER โดยไม่โยน Unknown Entity เป็น Actor, ทิศทางความสัมพันธ์เชิงเวลาที่เหตุการณ์ก่อนหน้าต้องชี้ไปยังเหตุการณ์ถัดไป (\texttt{precedes}), การรับประกันความสอดคล้องของการจัดเก็บข้อมูลข้ามโพรเซสผ่าน \texttt{InterProcessFileLock} ร่วมกับ \texttt{model\_copy(deep=True)}, และการทดสอบขอบเขตเวลาแกนเรื่องราว (\texttt{episode\_key}) ไม่ให้เกิดการเชื่อมโยงข้ามฤดูกาล

ประการที่สอง การทดสอบการคงทนของเวกเตอร์ศูนย์กลาง (Story Identification \& Centroid EMA Invariants) ได้รับการตรวจสอบผ่าน \texttt{test\_story\_service.py} โดยทดสอบว่าบทความข่าวที่มีค่าความคล้ายคลึงโคไซน์ $\cos \ge 0.85$ จะต้องถูกรวมเข้ากลุ่มประเด็นข่าวเดิมเสมอ (Direct Merge) แม้ไม่มีเอนทิตีร่วมกัน ในขณะที่บทความในแถบก้ำกึ่ง $0.74 \le \cos < 0.85$ จะถูกรวมก็ต่อเมื่อตรวจพบเอนทิตีบุคคล สถานที่ หรือองค์กรตรงกันอย่างน้อย 1 รายการ (Confirmed Merge) และหาก $\cos < 0.74$ ระบบจะต้องสร้างกลุ่มข่าวใหม่เสมอ แม้ว่าจะมีเอนทิตีร่วมกัน เพื่อป้องกันการรั่วไหลของคำศัพท์ที่ไม่เกี่ยวข้อง นอกจากนี้ การทดสอบคณิตศาสตร์ของ Centroid EMA ($\alpha = 0.85$) ยืนยันว่าจุดศูนย์กลางของกลุ่มข่าวสามารถรักษาสมดุลของแกนเรื่องเดิมได้อย่างมั่นคง ไม่เกิดการเบี่ยงเบนของความหมาย (Semantic Drift) แม้มีข่าวเข้ามาเสริมต่อเนื่องข้ามสัปดาห์ (\texttt{test\_long\_running\_storyline.py}) พร้อมทดสอบการสลับสถานะของประเด็นข่าวระหว่าง Active และ Dormant และการฟื้นคืนสถานะโดยคงรหัส \texttt{story\_id} เดิมอย่างคงเส้นคงวา (Idempotent Reactivation)

ประการที่สอง การทดสอบคุณสมบัติคงที่ของเอนจินจัดอันดับความนิยมแบบดีเทอร์มินิสติก (Deterministic Trending \& Adversarial Invariants) ตรวจสอบผ่าน \texttt{test\_trending\_deterministic.py} และ \texttt{test\_adversarial\_layer2\_layer3.py} โดยมีคุณสมบัติสำคัญที่ต้องผ่านการทดสอบ 3 ประการ คือ คุณสมบัติปลอดการเรียกใช้โมเดลภาษาขนาดใหญ่ (Zero LLM Invariant) ที่ยืนยันว่าไม่มีการเรียกใช้บริการภายนอกหรือ LLM ในกระบวนการคำนวณคะแนน ทำให้ความเร็วในการจัดอันดับคงที่ในระดับมิลลิวินาทีเสมอ คุณสมบัติความแน่นอนเชิงคณิตศาสตร์ (Strictly Deterministic Across Repeated Runs) ที่ทดสอบการคำนวณคะแนนซ้ำบนชุดข้อมูลข่าว 1,000 ข่าวแล้วได้คะแนนและลำดับเหมือนเดิมทุกประการร้อยละ 100 และการทดสอบกลไกลดทอนข่าวประจำวัน (Routine News Dampening) ที่ยืนยันว่ารายงานสภาพอากาศและผลสลากกินแบ่งรัฐบาลจะถูกคูณลดทอนคะแนนลงเหลือ 0.25 เท่าเสมอ เพื่อป้องกันไม่ให้ข่าวประจำวันบดบังข่าวด่วนที่สำคัญ นอกจากนี้ \texttt{test\_trending\_challenger\_stress.py} ยังทดสอบการจัดการกับเวลาในอนาคต (Future Timestamp Clamping) และเวลาในอดีตลึกเกิน 100 วัน (Underflow Safety) เพื่อความปลอดภัยทางคณิตศาสตร์

ประการที่สาม การทดสอบการประมวลผลพร้อมกันและการป้องกันภาวะตื่นตระหนกของแคช (Concurrency \& Cache Stampede Protection) ตรวจสอบผ่าน \texttt{test\_summary\_cache.py} และ \texttt{test\_sqlite\_news\_repo.py} โดยระบบได้จำลองสถานการณ์ที่มีผู้ใช้งานส่งคำขอสรุปข่าวบทความเดียวกันเข้ามาพร้อมกัน 100 คำขอในเสี้ยววินาทีเดียวกัน กลไก Single-Flight Mutex Locking จะอนุญาตให้คำขอแรกเพียงคำขอเดียวส่งต่อไปยัง KKU Gen.AI API ในขณะที่อีก 99 คำขอจะรอรับผลลัพธ์จากแคชเดียวกัน ช่วยป้องกันไม่ให้โควตา API ถูกใช้สิ้นเปลืองและป้องกันการล่มของระบบเซิร์ฟเวอร์ และสำหรับการบันทึกข้อมูลแบบหลายเธรดใน SQLite โหมด Write-Ahead Logging (WAL) ได้รับการทดสอบการอ่านและเขียนพร้อมกันจำนวนมหาศาลโดยไม่เกิดข้อผิดพลาดฐานข้อมูลถูกล็อก (Database Locked Error)

ประการที่สี่ การทดสอบความมั่นคงปลอดภัยและการคุ้มครองข้อมูลส่วนบุคคล (Zero-PII Compliance \& PDPA Testing) ตรวจสอบผ่าน \texttt{test\_storage\_pdpa.py} โดยทำการตรวจสอบยืนยันเชิงลึก (Deep Structural Assertion) ว่าในฐานข้อมูลไม่มีการบันทึกหมายเลขที่อยู่ไอพี (IP Address) ข้อมูล User Agent ข้อมูลตำแหน่งพิกัดทางภูมิศาสตร์ หรือชื่อบุคคลของผู้ใช้งานแม้แต่จุดเดียว โดยข้อมูลพฤติกรรมความสนใจจะถูกบันทึกเป็นเพียงตัวเลขคะแนนรวมแบบนิรนาม (Anonymous Aggregate Engagement) เท่านั้น ตลอดจนทดสอบฟังก์ชันการล้างข้อมูลประวัติบนเบราว์เซอร์ (Clear Data Feature) ว่าสามารถคืนสถานะความเป็นส่วนตัวของผู้ใช้ได้อย่างสมบูรณ์

ประการที่ห้า การทดสอบชุดประเมินผลเชิงประจักษ์ (Evaluation Harness Testing) ตรวจสอบผ่าน \texttt{test\_evaluation\_harness.py} โดยทดสอบความถูกต้องของกระบวนการคำนวณเมตริก B-cubed Precision, B-cubed Recall, B-cubed F1-score และ Pairwise Metrics กับข้อมูลข่าวจริง 111 ข่าว และ 59 เหตุการณ์อ้างอิง เพื่อให้มั่นใจว่าเครื่องมือวัดผลทางสถิติของระบบทำงานได้อย่างถูกต้อง แม่นยำ และสอดคล้องกับระเบียบวิธีวิจัยมาตรฐานสากล

ประการที่หก การทดสอบแบบจำลองหลักฐานเชิงเหตุการณ์และการตรวจจับข่าวไม่เกี่ยวข้อง (Event Evidence Intelligence \& Outlier Detection Testing) ตรวจสอบผ่าน \texttt{test\_event\_evidence.py} โดยทดสอบ 3 มิติสำคัญ ได้แก่ การทดสอบกลไกสำรองการประมวลผลเชิงศึกษาหลักฐาน (Heuristic Corroboration Fallback) ที่จำลองกรณีไม่มีการเชื่อมต่อกับโมเดลภาษาขนาดใหญ่ โดยระบบจะต้องสกัดพัฒนาการเหตุการณ์ตามลำดับเวลาและระบุแหล่งข่าวที่ยืนยันตรงกันได้อย่างครบถ้วนสมบูรณ์โดยมีความหน่วงเวลา 0 มิลลิวินาที การทดสอบความถูกต้องของการสกัดโครงสร้างข้ออ้าง (Claim-Level Evidence Parsing) จากเนื้อหาข่าวจริงที่สามารถจำแนกหมวดหมู่ข้ออ้างและระบุรหัส \texttt{article\_id} อ้างอิงได้อย่างถูกต้อง และการทดสอบระบบแคชลายนิ้วมือ SHA-256 (Fingerprint Caching) ที่รับประกันความแน่นอนเชิงผลลัพธ์ (Deterministic Replay) และป้องกันการสิ้นเปลืองโควตาการประมวลผลซ้ำ

ประการที่เจ็ด การทดสอบระบบสืบค้นเจาะประเด็นข่าวแบบอ่านอย่างเดียวและความมั่นคงปลอดภัยของตัวแยกวิเคราะห์ (Issue Explorer Read-Only \& Query Safety Invariants) ตรวจสอบผ่าน \texttt{test\_issue\_explorer.py} (TC-08 ถึง TC-13) โดยมีคุณสมบัติสำคัญที่ต้องผ่านการทดสอบ ได้แก่ การทดสอบความถูกต้องและปลอดภัยของตัวแยกวิเคราะห์คำค้นหา (Query Parser) ที่รองรับตรรกะ AND, OR, NOT และวลีเฉพาะเจาะจงพร้อมทั้งหลบอักขระพิเศษเพื่อป้องกันการโจมตี SQL Injection การทดสอบการันตีโหมดอ่านอย่างเดียว (Read-Only Mode Invariant ผ่าน \texttt{mode=ro}) ที่รับประกันว่าการสืบค้นข้อมูลเชิงวิเคราะห์จะไม่มีคำสั่งเขียนหรือเปลี่ยนแปลงข้อมูลในฐานข้อมูล SQLite ข่าวหลัก การทดสอบความคงทนของการรวมกลุ่มประเด็นย่อยและการคัดกรองข่าวหลุดประเด็น (Outlier Filtering Regression) ตลอดจนการทดสอบการควบคุมอัตราคำขอ (Rate Limiting) และสวิตช์ตัดการทำงานฉุกเฉิน (Kill Switch Contract)

ประการที่แปด การทดสอบความสอดคล้องของแคชระดับโพรดักชันและการตรวจสอบก่อนส่งมอบ (Production Cache Consistency \& Pre-flight Invariants) ตรวจสอบผ่าน \texttt{scripts/preflight\_test.py} และ \texttt{test\_layer4\_stress.py} เพื่อรับประกันว่าไม่มีการรั่วไหลของไฟล์สคริปต์รุ่นเก่าบน Edge Cache ของ Cloudflare CDN และ Service Worker โดยตรวจสอบว่าทุกคำขอสำหรับไฟล์สคริปต์คงที่ได้รับส่วนหัว \texttt{Cache-Control} ที่ระบุ \texttt{no-cache, must-revalidate} เสมอ พร้อมทั้งทดสอบผ่าน Headless Browser อัตโนมัติว่าไม่มีข้อผิดพลาดหลุดรอดบนหน้าจอ (Zero Console Error) และสัญญาณการเชื่อมต่อแบบเรียลไทม์เปลี่ยนสถานะเป็น LIVE อย่างสมบูรณ์ก่อนการปล่อยระบบขึ้นสู่สภาพแวดล้อมจริง
