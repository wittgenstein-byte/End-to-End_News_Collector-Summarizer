\subsection{ชุดข้อมูลและการเตรียมข้อมูล (Datasets \& Data Preprocessing)}

การวิจัยและพัฒนาโมเดลจำแนกหมวดหมู่ข่าวภาษาไทย 9 หมวดหมู่หลัก (การเมือง, เศรษฐกิจ, เทคโนโลยี, สุขภาพ, สิ่งแวดล้อม, กีฬา, บันเทิง, สังคม, ต่างประเทศ) ใช้ชุดข้อมูลมาตรฐาน 2 แหล่งหลัก ได้แก่ ชุดข้อมูล ThaiSum ซึ่งเป็นคลังข้อมูลข่าวภาษาไทยขนาดใหญ่ที่รวบรวมจากสำนักข่าวชั้นนำ ได้แก่ ไทยรัฐ ไทยพีบีเอส เดลินิวส์ และประชาไท รวมกว่า 350,000 บทความ พร้อมการระบุหมวดหมู่และบทสรุปอย่างเป็นทางการ และชุดข้อมูล Prachathai-67k ซึ่งเป็นคลังข้อมูลบทความข่าวเชิงลึกด้านการเมือง สังคม และสิ่งแวดล้อม จำนวน 67,889 บทความ


กระบวนการเตรียมข้อมูล (Data Preprocessing Pipeline) เริ่มต้นจากการทำความสะอาดข้อความ ขจัดแท็ก HTML สัญลักษณ์พิเศษ และการเว้นวรรคที่ซ้ำซ้อน จากนั้นทำการตัดคำภาษาไทยด้วยไลบรารี PyThaiNLP โดยใช้อัลกอริทึม \texttt{newmm} (Dictionary-based Maximal Matching ผสาน TCC) และคัดกรองคำภาษาไทยที่ไม่สื่อความหมายออก แล้วจึงแบ่งชุดข้อมูลออกเป็นชุดฝึกสอน ชุดตรวจสอบ และชุดทดสอบ (Stratified Train/Validation/Test Split) ในอัตราส่วน 70:15:15 เพื่อคงการกระจายตัวของทั้ง 9 หมวดหมู่ให้สมดุล

\subsection{วิธีการฝึกสอนโมเดล (Model Training Methodology)}

ในการทดลองและฝึกสอนโมเดลจำแนกหมวดหมู่ข่าว ระบบได้ทำการพัฒนา 3 แนวทางหลัก ได้แก่ การประยุกต์ใช้โมเดล Linear Support Vector Classifier (LinearSVC) ร่วมกับการแปลงเวกเตอร์ข้อความด้วย \texttt{TfidfVectorizer} ที่กำหนดขนาดฟีเจอร์สูงสุด 20,000 คำ และผ่านการสอบเทียบความน่าจะเป็น (Probability Calibration) ด้วย \texttt{CalibratedClassifierCV} เพื่อให้ได้ค่าความเชื่อมั่นของแต่ละหมวดหมู่ การปรับจูนโมเดลการเรียนรู้เชิงลึก (Fine-tuned WangchanBERTa Transformer) บนสถาปัตยกรรม RoBERTa โดยเพิ่ม Linear Classification Head ด้านบน และฝึกสอนด้วย Cross-Entropy Loss ผ่าน AdamW Optimizer และการออกแบบไปป์ไลน์จำแนกแบบหลายชั้น (3-Tier Cascade Classifier) ในระบบจริง ซึ่งเริ่มจากการตรวจจับคำสำคัญเฉพาะกลุ่มที่มีความแม่นยำสูง (Tier 1: Regex \& Keyword Cues) หากความเชื่อมั่นไม่ถึงเกณฑ์จึงส่งต่อให้โมเดล LinearSVC ประมวลผล (Tier 2) และมีโมเดล WangchanBERTa ทำหน้าที่รองรับกรณีข้อความที่มีความกำกวมสูง (Tier 3)

\subsection{การประเมินประสิทธิภาพการจัดกลุ่มข่าวแบบสองชั้น (Two-Layer Story Identification Benchmark)}

เพื่อประเมินความถูกต้องของสถาปัตยกรรมจัดกลุ่มข่าวสารใหม่ที่แยกส่วนระหว่างการระบุประเด็นข่าว (Story Identification) กับการจัดอันดับกระแสข่าว (Trending Engine) ตามข้อเสนอแนะของคณะกรรมการ โครงงานได้สร้างชุดข้อมูลทดสอบมาตรฐานภาคสนาม (Empirical Benchmark Dataset) จำนวน 111 บทความจริงจากคลังข้อมูลข่าวภาษาไทย ครอบคลุม 14 สำนักข่าว และ 9 หมวดหมู่ ซึ่งประกอบด้วยกลุ่มเหตุการณ์จริง (Ground Truth Events) จำนวน 59 เหตุการณ์ โดยมีทั้งเหตุการณ์วิกฤตที่ยืดเยื้อต่อเนื่องข้ามวันข้ามหมวดหมู่ เช่น อุทกภัยจังหวัดน่าน (28 บทความ ต่อเนื่อง 8 วัน ครอบคลุม 4 หมวดหมู่ ได้แก่ สิ่งแวดล้อม การเมือง สังคม และเศรษฐกิจ) ข่าวการฮั้วเลือกตั้งสมาชิกวุฒิสภา (15 บทความ ต่อเนื่อง 5 วัน) เหตุการณ์ระเบิดโพธิ์มิ่งจังหวัดปัตตานี รวมถึงกลุ่มข่าวประจำวันที่มีคำศัพท์คล้ายกันแต่เกิดขึ้นคนละวัน เช่น ราคาทองคำและราคาน้ำมัน เพื่อใช้เป็นชุดควบคุมเชิงลบ (Hard Negative Controls) ตลอดจนข่าวเดี่ยว (Singletons) อีก 52 เหตุการณ์

\subsection{การจัดกลุ่มมหากาพย์เหตุการณ์และการระบุพัฒนาการเรื่องราวระดับมหภาค (Stage B Macro-Event \& Story Identification)}

สถาปัตยกรรมการจัดกลุ่มข่าวสารของระบบแบ่งการทำงานออกเป็น 2 ชั้นอย่างชัดเจน ได้แก่ การระบุกลุ่มข่าวเหตุการณ์ย่อย (Stage A: Sub-Event Story Identification) ซึ่งจัดกลุ่มข่าวที่มีความคล้ายคลึงของข้อความและเอนทิตีสูง และการเชื่อมโยงการพัฒนาของประเด็นข่าวหลักที่มีเหตุการณ์ที่ข้ามช่วงเวลาและข้ามบริบท (Stage B: Macro-Event Identification) เพื่อติดตามเรื่องราวอย่างต่อเนื่อง (Storyline Tracking)

อย่างไรก็ดี ในบริบทของข่าวภาษาไทย การระบุเหตุการณ์ต่อเนื่องมักเจอความยาก คือ \textbf{ข่าวที่มีความคล้ายคลึงกัน ไม่จำเป็นต้องเป็นข่าวของเหตุการณ์เดียวกัน และข่าวที่เป็นเหตุการณ์เดียวกันก็ไม่จำเป็นต้องมีความคล้ายคลึงกันสูงเสมอไป} หากใช้เพียงเวกเตอร์ความคล้ายคลึง (Cosine Similarity) ระบบจะเกิดปัญหาการรวมกลุ่มแบบลูกโซ่ (Chain Merging / Semantic Drift) ที่ดึงข่าวคนละเรื่องมารวมกัน ระบบจึงได้วางกฎและคุณสมบัติคงที่ทางวิศวกรรม (Invariants) 5 มิติหลัก ได้แก่:

\begin{enumerate}
    \item \textbf{การแปลงข้อความภาษาไทยและลำดับชั้นสถานที่ (Thai Normalization \& Location Hierarchy)}\\*
      :
    ระบบพัฒนาโมดูล \texttt{thai\_normalizer.py} แปลงตัวเลขไทย (๐--๙) เป็นเลขอารบิก ลบอักขระความกว้างศูนย์ ขยายตัวย่อหน่วยงานและสถานที่สำคัญ (เช่น รพ., สน., สตช., กทม.) พร้อมทั้งสร้างโครงสร้างข้อมูลลำดับชั้นทางภูมิศาสตร์ 3 ระดับ (\textit{sub\_location $\rightarrow$ district $\rightarrow$ province}) ครอบคลุมทั้ง 77 จังหวัดทั่วประเทศไทย
    \item \textbf{การป้องกันการรวมกลุ่มที่ตรงกันเพียงแค่ชื่อจังหวัด (Strict Province-Only Veto)}\\*
      :
    ข่าวอุบัติเหตุหรืออาชญากรรมในไทยมักเกิดขึ้นในจังหวัดเดียวกันแต่เป็นคนละเหตุการณ์ (เช่น ข่าวเรือล่มหน้าวัดพนัญเชิง กับ ข่าวอุบัติเหตุรถยนต์ในจังหวัดพระนครศรีอยุธยา) ระบบกำหนดคุณสมบัติว่า หากเปรียบเทียบข่าวแล้วพบว่าตรงกันเพียงแค่ชื่อจังหวัด โดยไม่มีอำเภอ ตำบล สถานที่เฉพาะ หรือตัวละครสำคัญตรงกัน ระบบจะบังคับไม่ให้รวมกลุ่มทันที (\texttt{score = 0.0}) พร้อมทั้งสกัดเอนทิตีแบบแยกประเภท (Typed NER: Person, Org, Loc, Facility) โดยไม่ส่งคำที่ไม่รู้จักหรือชื่อจังหวัดไร้คำนำหน้าไปปนกับรายชื่อตัวละคร (\texttt{actor\_names})
    \item \textbf{การกำหนดกรอบเวลาของแกนเรื่องราวข่าว (Episode-Scoped Storyline Anchors)}\\*
      :
    เหตุการณ์ที่เกิดขึ้นซ้ำตามฤดูกาล เช่น ``น้ำท่วมเชียงราย'' หรือ ``ไฟไหม้โรงงาน'' จะถูกจำกัดกรอบเวลาไม่เกิน 45 วัน (\texttt{anchor\_episode\_days = 45}) เพื่อป้องกันไม่ให้ข่าวน้ำท่วมคนละปีถูกผูกโยงเข้าเป็นประเด็นเดียวกัน
    \item \textbf{ทิศทางความสัมพันธ์กันของเวลาและการยืนยันสถานะ (Temporal Causality \& Relation Direction)}\\*
      :
    ความสัมพันธ์ระหว่างเหตุการณ์ย่อย (\texttt{EventRelationRecord}) ถูกกำหนดทิศทางตามเวลาเกิดเหตุจริง (\texttt{event\_time}) โดยเหตุการณ์ก่อนหน้าจะชี้ไปยังเหตุการณ์ถัดไป (\texttt{A precedes B}) และเริ่มต้นด้วยสถานะ \textit{inferred} ก่อนจะเลื่อนขั้นเป็น \textit{verified} เมื่อมีหลักฐานยืนยันข้ามสำนักข่าวอิสระ
    \item \textbf{การป้องกันการชนกันระหว่างแก้ไขและความสอดคล้องและถูกต้องของข้อมูล (Inter-Process File Lock \& SST Consistency)}\\*
      :
    พัฒนาระบบล็อกไฟล์ระดับเคอร์เนล (\texttt{InterProcessFileLock}) ที่ทำงานข้ามโพรเซสทั้งบน Linux (\texttt{fcntl}) และ Windows (\texttt{msvcrt}) พร้อมทั้งคืนค่าข้อมูลแบบ \texttt{model\_copy(deep=True)} จาก Repository เพื่อป้องกันไม่ให้ข้อมูลที่ถูกแคชในหน่วยความจำเกิดการข้ามเธรด และมีระบบชดเชยการย้อนกลับ (Compensating Rollback) หากการบันทึกสถานะระหว่าง Story และ Macro Event เกิดความล้มเหลวกลางคัน
\end{enumerate}

\subsection{เกตคัดกรองความเกี่ยวข้องและแบบจำลองหลักฐานเชิงเหตุการณ์ (Relevance Enforcement Gate \& Evidence Dossier)}

ในการวิเคราะห์และสังเคราะห์ข่าวสารจากหลายสำนักข่าว ระบบสรุปความแบบเดิมที่ใช้วิธีการนำข้อความข่าวทั้งหมดมารวมกันเป็นก้อนเดียวแล้วส่งให้โมเดลภาษาขนาดใหญ่ (Naive Text Concatenation Summarization) มักประสบปัญหาสำคัญ 3 ประการ ได้แก่ ปัญหาความเสี่ยงต่อการเกิดภาพหลอน (Hallucination) ปัญหาการสรุปความแบบกว้างและเหมารวมเกินไป (Generalized Summaries) ซึ่งมองข้ามความแตกต่างของมุมมองในแต่ละสำนักข่าว และปัญหาข่าวหลุดประเด็นไปปนเข้ากับไทม์ไลน์หลัก (Evidence Pollution)

เพื่อแก้ไขปัญหาดังกล่าว โครงงานนี้จึงได้ออกแบบกระบวนการทำงานแบบ 3 ขั้นตอนที่บังคับให้ใช้ผลการคัดกรอง (Enforced Multi-Stage Pipeline) ประกอบด้วย:

\begin{enumerate}
    \item \textbf{Stage 1: การกรองตามความเกี่ยวข้อง (Event Relevance Gate)}\\*
      :
    ทำการคัดแยกข่าวทั้งหมดในกลุ่ม (Candidate Articles เช่น 33 บทความ) ออกเป็น 3 กลุ่ม ได้แก่ \textit{Relevant Evidence} (ข่าวที่เป็นพยานหลักฐานของเหตุการณ์หลักโดยตรง เช่น 9 บทความ), \textit{Context Articles} (ข่าวที่เป็นเพียงบริบทแวดล้อมหรือภูมิหลังทางการเมือง), และ \textit{Excluded Articles} (ข่าวที่ไม่เกี่ยวข้องกับเหตุการณ์) พร้อมบันทึกเหตุผลประกอบ
    \item \textbf{Stage 2: การสังเคราะห์ความคืบหน้าจากหลักฐานจริง (Event Progression Synthesis)}\\*
      :
    ส่งเฉพาะบทความในกลุ่ม \textit{Relevant Evidence} เท่านั้นไปยังโมเดลภาษาขนาดใหญ่เพื่อสร้างบทสรุป ไทม์ไลน์ และข้อเท็จจริงยืนยัน ซึ่งช่วยลดจำนวนโทเค็นลงกว่าร้อยละ 70 และกำจัดสัญญาณรบกวนทางความหมาย
    \item \textbf{Stage 3: สอบความถูกต้องของผลลัพธ์ (Output Validator)}\\*
      :
    ตรวจสอบว่ารหัสอ้างอิง (\texttt{article\_id}) ในไทม์ไลน์และข้อเท็จจริงทุกข้อต้องอยู่ในชุด \textit{Relevant Evidence} เท่านั้น หากพบการอ้างอิงข่าวหลุดประเด็น ระบบจะสั่งปฏิเสธ (Hard Reject) และทดลองสังเคราะห์ใหม่ 1 ครั้ง (Bounded Retry) หากยังไม่ถูกต้องจะสลับไปใช้ผลลัพธ์เชิงฮิวริสติก (Deterministic Baseline Fallback) ทันที
\end{enumerate}

โครงสร้างข้อมูลของแฟ้มวิเคราะห์ความคืบหน้านำเสนอผ่าน 4 มิติหลัก ได้แก่:

ประการแรก พัฒนาการของเหตุการณ์ตามลำดับเวลา (Progression Timeline) โมเดลจะจำแนกหมวดหมู่วิวัฒนาการของเหตุการณ์ออกเป็นระยะต่าง ๆ เช่น จุดเริ่มต้น พัฒนาการหลัก และความคืบหน้าล่าสุด พร้อมระบุช่วงเวลา สรุปความหมายของเหตุการณ์ และแนบรหัสหลักฐานอ้างอิงย้อนกลับไปยังบทความข่าวต้นทาง

ประการที่สอง ข้อเท็จจริงที่ได้รับการยืนยันตรงกัน (Confirmed Facts) โมเดลจะคัดกรองเฉพาะข้อมูลข้อเท็จจริงที่มีการรายงานตรงกันจากสำนักข่าวพตั้งแต่ 2 แห่งขึ้นไป (Corroborating Sources) พร้อมระบุระดับความเชื่อมั่นและรหัสหลักฐาน เพื่อให้ผู้อ่านได้รับข้อมูลที่ผ่านการตรวจสอบยืนยัน

ประการที่สาม ตารางเปรียบเทียบจุดยืนและข้อขัดแย้ง (Conflict Matrix) ในกรณีที่ประเด็นข่าวมีข้อพิพาทหรือความคิดเห็นที่แตกต่างกัน โมเดลจะสกัดหัวข้อข้อพิพาท ระบุผู้แถลง สำนักข่าวที่รายงาน จุดยืน และข้อความอ้างอิงของแต่ละฝ่าย ช่วยให้ผู้อ่านเห็นภาพรวมความขัดแย้งอย่างเป็นกลางและรอบด้าน

ประการที่สี่ สิ่งที่ยังไม่ทราบและจุดบอด (Unknowns and Blindspots) โมเดลจะทำการวิเคราะห์ช่องว่างของข้อมูล ระบุคำถามสำคัญที่ยังไม่มีคำตอบ และข้อปฏิบัติหรือการสืบสวนที่ยังอยู่ระหว่างรอคอยผล เพื่อเตือนผู้อ่านไม่ให้ด่วนสรุปข้อมูลที่ยังไม่สมบูรณ์

นอกจากนี้ บนส่วนต่อประสานผู้ใช้จะแสดงสถิติความโปร่งใส (Dossier Metrics) เช่น จำนวนข่าวในกลุ่มเบื้องต้น จำนวนข่าวที่คัดแยกออก และจำนวนสำนักข่าวที่ยืนยันตรงกัน พร้อมทั้งกลไกแคชลายนิ้วมือ SHA-256 ช่วยป้องกันการเรียกประมวลผลซ้ำโดยไม่จำเป็น


\subsection{สถาปัตยกรรมระบบเจาะประเด็นข่าวและการสืบค้นเชิงวิเคราะห์ (Issue Explorer \& Read-Only Query Architecture)}

นอกเหนือจากการติดตามกระแสข่าวสารรายวันและประเด็นเหตุการณ์แล้ว ระบบยังได้พัฒนาสถาปัตยกรรมย่อยสำหรับเจาะประเด็นข่าวและการสืบค้นเชิงวิเคราะห์ (Issue Explorer Architecture) ซึ่งได้รับการออกแบบภายใต้หลักการ Vertical Slice Architecture เพื่อแยกขอบเขตการทำงาน (Separation of Concerns) ของระบบสืบค้นเชิงลึกออกจากวงรอบการดึงข่าวหลัก พร้อมติดตั้งระบบปิดการทำงานฉุกเฉิน (Kill Switch ผ่าน \texttt{settings.issue\_explorer\_enabled}) ที่ช่วยให้ผู้ดูแลระบบสามารถเปิดหรือปิดกั้นการเข้าถึงฟังก์ชันนี้ได้ทันทีโดยไม่กระทบต่อการทำงานของระบบหลัก

การรักษาความปลอดภัยและความถูกต้องของข้อมูลข่าว (Data Integrity Guarantee) ออกแบบผ่านโมดูล \texttt{SqliteReadOnlyArticleSource} ที่บังคับเชื่อมต่อฐานข้อมูล SQLite ในโหมดอ่านอย่างเดียว (Read-Only Mode ผ่าน URI \texttt{file:data/news\_data.db?mode=ro}) เพื่อป้องกันความเสี่ยงที่การสืบค้นข้อมูลจำนวนมากจะเข้าไปแทรก ล็อก หรือเขียนทับข้อมูลของ Scraper Service ซึ่งทำงานร่วมกับโหมด Write-Ahead Logging (WAL) ได้อย่างเสถียร

ตัวแยกวิเคราะห์คำค้นหา (Query Parser) ได้รับการออกแบบให้รองรับไวยากรณ์การค้นหาขั้นสูง (Advanced Boolean Query Syntax) ประกอบด้วย
\begin{enumerate}
    \item \textbf{การค้นหาแบบเชื่อมความสัมพันธ์เชิงร่วม (Logical AND)}\\*
      ดำเนินการโดยการเว้นวรรคระหว่างคำค้นหา
    \item \textbf{การค้นหาแบบเลือกเงื่อนไข (Logical OR)}\\*
      ดำเนินการโดยการใช้เครื่องหมายไปป์ (\texttt{|}) คั่นระหว่างคำที่ต้องการ
    \item \textbf{การคัดกรองคำที่ไม่เกี่ยวข้องออก (Negation หรือ Exclude)}\\*
      ดำเนินการโดยการใส่เครื่องหมายลบ (\texttt{-term}) นำหน้าคำที่ไม่ต้องการ
    \item \textbf{การค้นหากลุ่มคำเฉพาะเจาะจง (Quoted Phrase Search)}\\*
      ดำเนินการโดยการครอบกลุ่มคำด้วยเครื่องหมายคำพูดคู่ (\texttt{"..."})
\end{enumerate}
พร้อมทั้งมีระบบการทำความสะอาดและหลบอักขระพิเศษ (Sanitization \& Wildcard Escaping) เพื่อป้องกันการโจมตีแบบ SQL Injection และป้องกันความผิดพลาดจากอักขระพิเศษในคำสั่ง \texttt{LIKE} ของฐานข้อมูล

นอกจากนี้ ระบบยังมีโมดูลพจนานุกรมขยายคำพ้องความหมายและคำย่อหน่วยงานรัฐ (Synonym \& Acronym Expansion Dictionary) ที่สามารถแปลงคำย่อทางการเมืองและหน่วยงานราชการไทย เช่น สตง., ป.ป.ช., กกต., ครม. และ ดีเอสไอ ให้เป็นชื่อเต็มและกลุ่มคำที่เกี่ยวข้องโดยอัตโนมัติ ช่วยให้ผลการสืบค้นมีความครอบคลุมสูง โดยเอนจินวิเคราะห์ประเด็นข่าว (\texttt{analyzer.py}) จะทำการจัดกลุ่มประเด็นย่อย (Issue Sub-clusters) สกัดตัวละครและองค์กรสำคัญ สรุปไทม์ไลน์การเคลื่อนไหวตามลำดับเวลา และวิเคราะห์สัดส่วนมุมมองของแต่ละสำนักข่าว (Publisher Perspective Breakdown) พร้อมกลไกคัดกรองข่าวที่หลุดประเด็น (Outlier Filtering) และควบคุมอัตราการเรียกใช้งานผ่านระบบ Sliding Window IP Rate Limiting ที่สามารถสกัดหมายเลข IP จริงของผู้ใช้ผ่านส่วนหัวของ Cloudflare (\texttt{CF-Connecting-IP}) และ \texttt{X-Forwarded-For} ได้อย่างแม่นยำ


\subsection{มาตรการเพิ่มความปลอดภัยและความเสถียรของระบบ (Production Hardening \& Reliability Guardrails)}

ในการนำระบบขึ้นสู่สภาพแวดล้อมการใช้งานจริงบนคลาวด์ร่วมกับ Nginx, Cloudflare CDN และ Progressive Web App (PWA) ระบบต้องเจอกับจุดเปราะบางสำคัญ ที่ระบบได้แก้ไขและวางมาตรการป้องกันเชิงรุก (Reliability Guardrails) 4 ประการหลัก ดังนี้

ประการแรก การป้องกันปัญหาความไม่สอดคล้องของแคชระหว่าง Edge และ Client (Edge \& Client Cache Inconsistency) เกิดจากการที่ Cloudflare และ Service Worker แคชไฟล์ JavaScript โมดูลย่อย (ES Modules) ไว้ต่างเวอร์ชันกัน ทำให้เกิดข้อผิดพลาดในการโหลดโมดูล ระบบจึงได้กำหนดนโยบาย \texttt{NoCacheStaticFiles} บน FastAPI ส่งส่วนหัว \texttt{Cache-Control: no-cache, must-revalidate} สำหรับไฟล์สคริปต์หน้าบ้านทั้งหมด พร้อมทั้งติดตั้งระบบ Version Query Tagging (\texttt{?v=3.3.3}) ในจุดเชื่อมต่อโมดูลย่อยทุกจุด และติดตั้งสคริปต์ล้างแคชเก่าอัตโนมัติเมื่อ Service Worker อัปเดตเวอร์ชันใหม่

ประการที่สอง การเข้าได้กับสภาพแวดล้อมระบบปฏิบัติการที่ต่างกันได้ (Cross-OS Native Dependency Isolation) ซึ่งแก้ไขปัญหาความแตกต่างระหว่างสภาพแวดล้อมการพัฒนาบน Windows และสภาพแวดล้อมโพรดักชันบน Linux Docker ในส่วนการโหลดโมเดลตัดคำและเวกเตอร์ภาษาไทย โดยบังคับโหลดผ่าน \texttt{PreTrainedTokenizerFast} โดยตรงจากไฟล์ \texttt{tokenizer.json} ตัดปัญหาฟอร์แมตไม่เข้ากัน SentencePiece

ประการที่สาม กลไกเสถียรภาพของช่องทางการสื่อสารเรียลไทม์ (Dual-Transport Real-Time Fallback) รองรับการสลับช่องทางการเชื่อมต่อระหว่าง Secure WebSocket และ HTTP Long-Polling โดยอัตโนมัติ พร้อมทั้งมีระบบบันทึกโทรมาตรข้อผิดพลาด (\texttt{connect\_error} telemetry) ช่วยให้ระบบหน้าบ้านสามารถแสดงผลสถานะการเชื่อมต่อได้อย่างถูกต้อง ไม่ค้างที่สถานะออฟไลน์

ประการที่สี่ ตรวจสอบความพร้อมก่อนขึ้นโพรดักชันอัตโนมัติ (Automated Production Pre-flight Smoke Test Suite ผ่าน \texttt{scripts/preflight\_test.py}) ทำหน้าที่ตรวจสอบความสมบูรณ์ 5 มิติ ได้แก่ ความพร้อมของระบบจัดเก็บข้อมูลผ่าน \texttt{/readyz}, การทำงานของเอนจินจัดอันดับเทรนด์, การทดสอบหน้าเว็บผ่าน Headless Chromium เพื่อยืนยันว่าไม่มีข้อผิดพลาดบน Console (Zero Console Error Invariant), การตรวจสอบสถานะการเชื่อมต่อ WebSocket สด และการตรวจสอบส่วนหัว Cache-Control รวมถึงความพร้อมของระบบเจาะประเด็นข่าว ก่อนเปิดให้ผู้ใช้ภายนอกเข้าใช้งานจริง
